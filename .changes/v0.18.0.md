## v0.18.0 - 2026-11-27

No name is added, removed or moved, and no signature changes: the API check finds no break since v0.17.0. What a name does changes in two places: in `sandbox`, `RunHolding` and `Check` hold the program itself to the folders, which breaks some callers on Linux and macOS (under Changed and Security below); in `proc` on Windows, a start puts its process in a job that ends it sooner (under Security). One promise in `api/contract.txt` changes, as `api/breaks/v0.17.0.contract.txt` records: on macOS the files profile now also denies every exec but of a file beneath the folders and of `/usr/bin/true`, the dry run's program. Ten promises are added, all in `sandbox`, and two `gitenv` promises that held on Linux and macOS now hold on Windows too. Nothing changes in `service` or `load`, `gitenv` changes only in its tests, and no require in go.mod changes. The tagged tree is 11,981 non-test Go lines outside `internal/` (`task size`), at its ceiling of 11,981, up 523 (4.6%) from v0.17.0's 11,458: 305 for holding the program in `RunHolding`, 104 for the Windows start's guard job, 36 for reading a `#!` line as macOS does and holding a file that is no program to `/bin/sh`, and 78 for asking, before a refusal, what the kernel asks. The full release checks ran on macOS at the tagged commit; vet and the tests, with the race detector, ran on Linux, macOS and Windows at the tagged commit in CI. No full release checks ran on Linux or Windows for this release.

### For a v0.17.0 caller

Nothing changes for a program that does not call `sandbox.RunHolding`, or `sandbox.Check` with folders: every other name gives what it gave, and on Windows `proc.Start` and `proc.Run` give what they gave, with the process held in a job sooner. A caller of `RunHolding` names the program's real folder in `Folders`, starts the program by its real path, and names the folder of each program it starts. On Linux, a program that ran only because its `$ORIGIN` run path, or a library it names by its full path, had its folder added now needs that folder named. On macOS, a `#!` script needs its interpreter's folder named, a file the kernel hands to `/bin/sh` needs `/bin` named, and a program reached through `/tmp`, `/var` or `/etc` is named by its real path. Each refusal is `ErrUsage`, comes before anything is set, and names the folder it would need.

### Changed
* sandbox: `RunHolding`, and `Check` with folders, now hold the program itself to the folders, as they hold any file it opens. A program they do not hold is refused with `ErrUsage` before anything is set, and the error names the folder it would need; nothing is ever added to the folders for it. They follow the program's path as the kernel does, each symbolic link included, up to 40 links on Linux and 32 on macOS, to its real file, which must be beneath a folder the caller named or beneath its loader's own folder. On macOS each link on the path must be beneath a held folder too, since the system sandbox will not follow a link outside its folders, and so must a `#!` script's interpreter, taken as written from the script's first line, which ends at a newline or a `#`. The load folders `RunHolding` adds from the program's own bytes, its run path and the libraries it names never count toward holding the program. A dangling or empty link, a name after a file, and a path past the link limit are `ErrUsage` too. On macOS the profile now denies every exec but of a file beneath the folders, as Landlock already does on Linux, and of `/usr/bin/true`, the dry run's program. Breaking on Linux: a program in a folder the caller never named, whose run path has `$ORIGIN` or which names a library beside it by its full path, had that folder added and ran; it is now `ErrUsage`. A program whose real folder is not held, such as `/usr/bin/false` on Ubuntu 26.04, a link to `/usr/lib/cargo/bin/coreutils/false`, is now refused up front, where before the block was set and the exec failed with permission denied. Breaking on macOS, where the system sandbox did not hold a program's exec, each of these ran before and is now `ErrUsage`: a program in a folder the caller never named; a program reached through a link in a folder that is not held (`/tmp`, `/var` and `/etc` are such links); a `#!` script whose interpreter is outside the folders; and, while `/bin` is not held, a file the kernel refuses with ENOEXEC, which execvp then runs with `/bin/sh`. The kernel refuses so a file that may run with no `#!` and no Mach-O program's format (a Mach-O library or object is one), a `#!` line with no end in its first 512 bytes or with no interpreter, and a `#!` script whose interpreter is no Mach-O program, such as another script. A program the caller may not run, as the kernel asks it (by an execute bit in its mode, and by `faccessat(2)` with `X_OK` and the effective ids; a file of mode 0601 that the caller owns is one), and a `#!` script whose interpreter the caller may not run, are `ErrUsage` too, where before they failed after the exec with the system sandbox's exit 71. And a program behind the block can no longer start a program outside the folders, a shell's `/bin/sh` among them; on macOS `/usr/bin/true` is the one it still may. Name the program's real folder in `Folders`, start the program by its real path, and name the folder of each program it starts.

### Security
* sandbox: on macOS, a program behind `RunHolding`'s block could start programs outside the folders, and now starts only a program beneath them and `/usr/bin/true`, the dry run's program: the profile denies every other exec, as Landlock does on Linux. Before the block is set, `RunHolding` and `Check` with folders refuse with `ErrUsage` a program the block would not let run, naming what it would need: its real file and each link on its path, a `#!` script's interpreter, and `/bin/sh` for a file the kernel hands to the shell must each be beneath a held folder, and the caller must be allowed to run the program and its interpreter. What this breaks is under Changed.
* proc: on Windows, `Start` and `Run` put the process they start in a job that ends it, as the first call after the start returns. Before, a caller killed before a detached tree was whole left the leader suspended with no parent. Now the leader starts in an unnamed guard job set to kill on close, which is lifted once the leader is in its tree's own job and resumed. One window is left, and SECURITY.md lists it among what go-proc does not hold: a caller killed after Windows makes the process, inside `os/exec`'s start, and before that first call, still leaves the process suspended, in no job that ends it. On GitHub's Windows runner the window is about 5 ms of a 6 ms start. A process left so runs nothing, but holds its output, the files handed to it, its program file and its folder until it is ended, by `taskkill /f /pid <pid>` or by the end of its session. proc's docs say so too.
* proc, sandbox: the module holds itself to its four execs: the Linux shim's two, of its second stage and of the program, and the sandbox block's two, of the program on Linux and on macOS. Lint bans `syscall.Exec` and x/sys's `Exec`, and since a `//nolint` line passes lint, a test reads the module's source and fails on any other exec: another reference to either `Exec`, to the macOS block's `posix_spawn` exec, or to its trampoline outside the one file that makes it; a `//go:linkname` or `//go:cgo_import_dynamic` directive, or a reference to the runtime's raw syscall, anywhere else; an `import "C"` anywhere; and any file outside `testdata` that the go command builds into a package but is not Go, for any system or tag (C, C++, Objective-C, Fortran, assembly, headers, SWIG and `.syso` objects), but the macOS block's two `posix_spawn` trampolines, `sandbox/spawn_darwin_amd64.s` and `sandbox/spawn_darwin_arm64.s`. So cgo can come in by neither `import "C"` nor SWIG, and assembly only by those two files. A raw `execve` through `Syscall`, and what the two trampolines say, are held by review. A caller sees no change: no product code changes.
* gitenv: `api/contract.txt` now promises on Windows what it promised on Linux and macOS alone: a hook folder or file system monitor that the caller's environment names through `GIT_CONFIG_COUNT` and its pairs runs no program in a git started with `Env`'s result, and `GIT_DIR`, `GIT_WORK_TREE`, `GIT_INDEX_FILE`, `GIT_CONFIG`, `GIT_CONFIG_PARAMETERS` and `GIT_CONFIG_COUNT` in the caller's environment change nothing such a git reads or writes. `TestAProgramTheEnvironmentNamesRunsUnlessEnvDropsItsVariables` and `TestEachVariableThatMovesGitChangesNothingUnderEnv` now run Git for Windows too, under `Env` and, as their control, under the test process's own environment, where the hook and the monitor run and each variable moves git. No product code changes.
* sandbox: `api/contract.txt` now promises what `RunHolding`'s files block does to a real program, on all three systems, where before it promised only what the block asks of the kernel. `TestAProgramBehindRunHoldingReadsAndWritesBeneathItsFoldersAlone` runs the system's own copy program behind `RunHolding`: it copies a file beneath a read-only folder into a read-write one, and is refused a file outside the folders, a copy into a folder outside them, and a copy into the read-only folder. The same copies made with no block are its control. Where `Check` says the system gives no block, as on Windows, `RunHolding` refuses each run before the program starts, and nothing is copied. No product code changes.
* sandbox: a known limit, on Linux: a library a program behind `RunHolding` names by its full path, or finds by its run path, adds that library's real folder, and all beneath it, to what the program may read and run; a library whose folder is `/` or `/usr` itself is refused instead. So a program written into a read-write folder can read a folder the caller never named, if a shared library of the program's architecture lies there. A later release refuses such a library: one outside both the caller's folders and the loader's own default folders.

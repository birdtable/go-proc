## v0.5.0 - 2026-11-18

Fifteen names are added, eight are removed with no alias, three functions change their signature in place, and none is moved. The removed names, by package:

- `proc`: `Limits.ProcessData`, `CappedExec`, `Armed` and `Cmd.Armed`.
- `service`: `Need`, with its fields `Do`, `Means`, `Query`, `What` and `Why`, and `Plan.Needs`.
- `testenv`: `SkipOnWindows` and `Binary.Ldflags`.

`sandbox.Check`, `sandbox.Run` and `sandbox.RunHolding` keep their names and take or return something new (below). The names of `gitenv` and `load` do not change. The tagged tree is 10,112 non-test Go lines outside `internal/` (`task size`), at its ceiling of 10,112.

### Limits of this release

- **The Windows task folder's two-account check isn't run in this release.** `service.Install` on Windows now makes the folder for its `task.xml` private to the user (below). No run has yet tried, from a second account on the same machine, to change or replace that folder or its file.
- **The Linux sandbox checks ran on Docker Desktop's arm64 kernel**, not on amd64. These are the rows that need a privileged container with a delegated cgroup: a contained tree's tries to leave or lift its limit, a tree that meets its limit with no process to kill, a nested run, and a file's capabilities. Under amd64 emulation there the kernel gives no `clone3`, so the arm64 run is the record.

### Breaking for a v0.4.0 caller

- `proc` on Linux: the wrapper is gone, and with it `Limits.ProcessData`, `CappedExec`, `Armed` and `Cmd.Armed`, with no alias.
  - A `main` or `TestMain` that called `CappedExec(os.Args)` drops the call, and a `Cmd` drops `Armed`.
  - Linux no longer holds one process's data segment. `Limits.TreeMemory`, which v0.4.0 refused on Linux, takes its place there, held over the whole tree by a cgroup of the run's own (below).
  - Where systemd delegated no cgroup to the caller, `TreeMemory` is refused before anything starts; there is no fallback.
  - No run is refused after something started any more.
- `proc`: `Cmd.Drain` is honoured as given, with no default and no floor.
  - Zero now waits none: past the kill, a pipe a process still holds is cut at once and the run ends with `escaped`.
  - A caller that left `Drain` zero for the old 10 s sets `Drain: 10 * time.Second`.
  - On Windows a zero `Drain` is refused.
- `proc` on Windows: a `Cmd.Grace` above zero is refused. Windows sends no TERM a program can catch, so the job's kill always ended the tree at once and the grace was no time given. A Windows caller sets `Grace: 0` there and keeps its own grace elsewhere.
- `proc` on Linux: `Result.Peak` with `Cmd.ReadPeak` is the run's cgroup's `memory.peak`, the whole tree's memory at once, page cache included, not the largest resident set of one process. `Result.PeakKind` says which (below). Where no cgroup is delegated, or the kernel is older than 5.19, such a run goes with `PeakRead` false; v0.4.0 refused it without `Cmd.Armed`.
- `sandbox`: two signatures change in place, with no alias.
  - `Check(folders)` returns `(Block, error)`. `err := sandbox.Check(f)` becomes `_, err := sandbox.Check(f)`, or reads the `Block`.
  - `Run(args, environ)` is now `Run(path, args, environ)`, and `RunHolding(folders, args, environ)` is now `RunHolding(folders, path, args, environ)`: the program by its absolute path, then its arguments after its name, in place of a command line that began with `--`. `sandbox.Run([]string{"--", prog, a, b}, env)` becomes `sandbox.Run(prog, []string{a, b}, env)`.
  - `cmd/netblock` takes the same command line as before and prints the same usage.
- `service`: `Need` and `Plan.Needs` are gone, with no alias. The package carried them and never read them: it checked no need and met none. A caller that lists what a person must do before a unit runs, such as `loginctl enable-linger`, keeps that list beside its `Plan` and shows it itself.
- `service`: `Plan.Name` refuses a name that holds a capital letter, on every system (below).
- `service`: on macOS and Windows `State.Active` is now always false, with the new `State.ActiveKnown` false beside it. A caller that read a false `Active` as "not running" checks `ActiveKnown` first.
- `testenv`: `SkipOnWindows` is gone. A test that skips on Windows calls `t.Skip` where `runtime.GOOS` is `windows`, and gives its reason there.
- `testenv`: `Binary.Ldflags` is gone, and `Binary.X(name, value)` takes its place. `Ldflags("-X main.version=1.2.3")` becomes `X("main.version", "1.2.3")`, one `X` for each variable; a second `X` for the same name replaces the first. The other flags `Ldflags` took, `-s`, `-w` and `-buildid=<value>`, have no replacement.
- `testenv`: `Isolate`, and so `Main`, sets `GOENV=off` and no longer hands a test's go a copy of go's env file.
  - A setting made with `go env -w` (`GOPRIVATE`, `GOPROXY`, `GONOSUMDB`, `GOFLAGS`, `GOTOOLCHAIN`, `GOAUTH` and the rest) reaches a test's go only when the run sets it in the environment and the test's `Main` keeps it: `Main(m, testenv.Keep("GOPRIVATE"))`.
  - Without them, a test's go uses the toolchain's defaults, so a module missing from the cache is fetched from the public proxy and checked against the public checksum server by its path.
  - `Keep("GOENV")` no longer passes a file: `GOENV` passes only as `off`.
  - Why: no line of the person's env file reaches a test now. The copy left out each line it could see a credential on, but a credential in `GOFLAGS`, in a `GOPROXY` or `GONOSUMDB` URL, in a `.netrc` that `GOPRIVATE` sends go to, or behind `GOAUTH` now reaches a test only through a name the test keeps.
  - Not held: go still reads the toolchain's own `go.env`, in the root of the go on `PATH`, whatever `GOENV` says, and an image or a packager may put defaults there. `Isolate` does not pin those names against it.
- `testenv`: `Repo` commits on git's own default branch, no longer on `main`. That is the branch the host's git was built with, `master` before git 3.0. A test that assumed `main` asks git for the name (`git symbolic-ref --short HEAD`) or renames the branch (`git branch -m main`).
- `testenv`: `NoLeaks` is stricter. A package whose `TestMain` leaves a goroutine that never blocks now fails (below).

### Refusals a caller now meets

Each is made before any program starts.

- `proc`, wrapping `ErrRefused` and `errors.ErrUnsupported`:
  - on Linux, `Limits.TreeMemory` where no cgroup is delegated, naming why;
  - on Linux, `Limits.TreeMemory` or `Cmd.ReadPeak` from a process that is itself in a run's cgroup, as a program proc runs is, since its cgroup would go beside the outer one and out of its limit;
  - on Linux, `Limits.TreeMemory` where `/proc` is not a folder on a proc file system (a link to one included), naming why;
  - `Limits.Contained` where it cannot be held (listed under `proc` below);
  - on Windows, a `Cmd.Grace` above zero, and a zero `Cmd.Drain`.
- `proc` on Linux, wrapping `errors.ErrUnsupported`: `Start` and `Stop` where `/proc` is not the root of a proc file system, and where a container binds its own file over `/proc/sys/kernel/random/boot_id`, as LXC (with `lxc.autodev` on), Incus and systemd-nspawn do. A file bound below `/proc` is refused wrapping `syscall.EXDEV`. Neither starts or signals anything.
- `sandbox`, wrapping `ErrUsage`: a program not named by its absolute path, naming it. `ErrUsage`'s text no longer names a command or `--`.
- `service`, wrapping `ErrUsage`: a `Plan.Name` that holds a capital letter.
- `service` on Windows: an `Install` whose task folder does not keep the access it was made with, as on FAT or exFAT. The folder is removed.
- `testenv`: `Binary.X` with a name that is not an import path, a dot and a Go identifier, or a value that holds white space and both kinds of quote.

### proc

- Added: `Limits.Contained`, on Linux, holds the run's tree to `Limits.TreeMemory` against a process of the tree that moves itself out of the run's cgroup or writes its limit.
  - The program starts in user, cgroup, pid and mount namespaces of its own. The cgroup namespace is rooted at the run's cgroup, and the user namespace maps the caller's uid and gid each to itself.
  - It starts through a shim: the caller's own binary, run again before `main`. The shim writes 0 to the namespace's `user.max_cgroup_namespaces`, mounts the tree's own proc on `/proc`, sets `no_new_privs`, drops every capability and execs the program.
  - The kernel then refuses a process of the tree that moves out of the run's cgroup or writes its `memory.max` or `memory.swap.max`, and the run kills the tree itself once the cgroup counts an oom.
  - The tree may still write `-memory` to the `cgroup.subtree_control` of the run's parent, which takes the memory controller and the limit from the run's cgroup. While the caller runs, the run then kills the tree, from one inotify watch, and ends with an error that names the loss, never `limit`. It does the same when the cgroup's `memory.max` reads other than it set, or its `memory.events` cannot be read.
  - It holds the run's own cgroup alone: the tree may still write the files of another cgroup of the caller's user, another run's or the caller's.
  - Not held: the two above together. Every kill on a lost limit, like `Timeout` and the kill at the run's end, is made by the running caller, and the tree gets no signal when the caller dies. So a tree that first freezes or kills the caller's cgroup, then writes `-memory` to the parent's `cgroup.subtree_control`, runs on with no limit, and nothing kills it.
  - What it costs the program: it can make no cgroup namespace of its own. It is pid 1, so it ignores `SIGTERM` without a handler, reaps its tree's orphans and ends the tree as it exits. Its `/proc` lists its own tree alone. It sees its cgroup as `/` and other users' ids as 65534. A setuid file or a file's capabilities give it nothing.
  - What it costs the caller: the shim's memory counts in `TreeMemory`, and the caller's other `init` functions run in the shim. The shim starts with no environment, so no loader variable of the run's `Env` reaches it, and it hands the program its `Env` through a descriptor.
  - It is refused where the kernel, a security module or a container refuses an unprivileged user namespace, the shim's write or its proc mount, with the error inside; where cgroup v2 is not mounted with `nsdelegate`; without `TreeMemory`; with `Terminal`, whose terminal the tree could type into; to a caller whose effective uid is 0, as the tree would keep uid 0 and could write the kernel's global settings; and on Windows, where a process of the tree may clear its job's limit.
  - The zero `Cmd` runs as before.
- Added: `Result.PeakKind` names what `Result.Peak` counts, one of a closed list of `PeakKind`: `PeakTreeCharged` (Linux, the cgroup's charge for the whole tree), `PeakProcessResident` (the BSDs and macOS, one process's resident set), `PeakProcessCommitted` (Windows, one process's committed memory), and `PeakNone` where `PeakRead` is false. `Limits.TreeMemory`'s doc names what each system's cap holds. `Peak` and `PeakRead` are as they were.
- Changed, Linux: `Limits.TreeMemory` and `Cmd.ReadPeak` use a cgroup of the run's own, made beside the caller's cgroup in the parent systemd delegated (`Delegate=yes` with `DelegateSubgroup=`; the README gives the `systemd-run` line). The program starts in it, with no wrapper.
  - `TreeMemory` is that cgroup's `memory.max`, with no swap. A tree that passes it is killed whole and the run ends `limit`.
  - Not held: hugetlb pages are not charged to `memory.max` unless cgroup v2 is mounted with `memory_hugetlb_accounting` (Linux 6.7). So where the host keeps a hugetlb pool, a tree may map such pages past `TreeMemory`, uncounted in `Peak`, with `Contained` or without.
  - It holds a program that leaves its cgroup alone. A process of the tree runs as the caller's user, so it may write the cgroup's files or move itself to another cgroup under the delegated one, and is then out of the limit; one that moves is out of the kill at the run's end, and of the peak.
  - The cgroup is ended by `cgroup.kill` and removed at the run's end, with any cgroup its tree made in it. So a process of the tree that left its process group, or started a session of its own, is ended with the run, with `ReadPeak` alone too.
- Changed, Linux: `Cmd.ExtraFiles` and `Cmd.File` are no longer refused with `ReadPeak`. v0.4.0's note that a run through the wrapper starts it from `/proc/self/exe` without checking `/proc` no longer applies, as no run starts one.
- Changed: on Unix, a pipe no process holds when `Drain` ends is read for what it held then, so a zero `Drain` keeps output a program left buffered. On Windows every read is bounded by `Drain`. `Run` returns within `Timeout`, `Grace` and `Drain`; it could return 10 s past `Timeout` and `Grace` before. A short `Drain` gives an `escaped` end to a run whose killed member has not yet exited, or whose pipe is held, from fork to exec, by a program this process starts at the same moment.
- Fixed, Linux: a `Limits.TreeMemory` run ends `limit` only when its own cgroup's `memory.max` killed the tree. A tree that met its limit, got `ENOMEM` where the oom killer found no process to kill and exited 0, ended `limit`, as did one whose own cgroup beneath the run's killed part of it. Each now ends as its exit says. What is killed is unchanged.
- Security, Linux: a `Limits.TreeMemory` or `Cmd.ReadPeak` run reads which cgroup this process is in from `/proc/self/cgroup` only once `/proc` is a folder, not a link, on a proc file system. In a root whose `/proc` was another folder, a planted `self/cgroup` chose the run's cgroup. There `TreeMemory` is now refused, and a run that only reads its peak goes with `PeakRead` false.
- Security, Linux: `Start` and `Stop` open `/proc` once, check that it is the root of a proc file system, and read every file below that one descriptor, so a mount on `/proc`, or a rename of its folder, after the check is not read.
  - In a root whose `/proc` was a planted folder, `Stop` of an id whose leader was gone read a planted stat as the leader's and sent `SIGKILL` to the group that held its number.
  - Where the kernel gives `openat2`, no read crosses a mount: a file bound below `/proc`, as over a live leader's stat, is refused, wrapping `syscall.EXDEV`, and nothing is signalled. Before Linux 5.6, or where a filter refuses `openat2`, each file opened must be on the proc mount's own file system, so one bound from another is refused the same way.
  - `/proc/sys` is read only on the proc mount's own file system, so a mount there cannot choose the boot `Start` and `Stop` read.
  - Not held: on the `openat` route, a file or folder of the same proc mount bound over another is read as the kernel's; and a file system whose server answers `statfs` as proc, with the root's inode, as 9p may, is taken for proc.
  - A `Run`'s check for a group left behind reads `/proc` under the same check.
- Security, macOS: `Result.Left` no longer reads false while a process of the tree runs on. For a moment, a process whose exec is finishing as its parent exits is in no listing of its group, and a kill of the group does not find it. About once in 2,000 runs under load, of a program that starts a worker and exits, `Left` read false with the worker running. The group is now listed before the stop as well as after it, and a process in either listing counts, so `Left` reads true a little more often.
- Security, macOS: a tree kill, at a run's end or by `Stop`, no longer ends as done while such a process still runs past its exec. After a `SIGKILL` of the group, each process a listing held is asked with a kill of 0, which waits out an exec, and read by the `kern.proc.pid` sysctl. While one is live in the group, the group is killed again; past the kill tries the end is an error that the group still holds a live process. Before, 3 in 120,000 runs under load ended as done with the worker running.
- Security, Windows: `Limits.TreeMemory`, `Limits.Processes` and the job's hold on the tree are now stated limits in the doc and the README. A process of the tree runs as the caller's user, at its integrity, so it may open the caller, duplicate the job's handle from it, and then clear either limit, allow breakaway and start a process out of the job, clear kill-on-close, or keep the job alive past the caller's end. A test row shows it. Holding a hostile program needs another token (Low integrity or an AppContainer), which is a sandbox's job, not proc's.

### sandbox

- Changed: `Check` returns a `Block` with its yes: what the block closes on this system and what it leaves open, a field each for `Network`, `Daemons`, `Terminal`, `Signals` and `ServiceManager`. With a no it is the zero `Block`. On Linux every field is true. On macOS `Signals` and `ServiceManager` are false, as the profile allows a signal to a process outside the sandbox and launchd answers by the bootstrap port.
- Changed: `Run` and `RunHolding` take the program by its absolute path, then its arguments (above).

### service

- Added: `State.ActiveKnown`, true only where the tool answered whether the unit runs now: systemd on Linux, for a unit it holds and one it does not. On macOS and Windows it is false, and so is `Active`, as `launchctl print` and `schtasks /query /xml` give no machine-readable answer.
- Security: `Plan.Name` refuses a name that holds a capital letter, on every system. Task Scheduler reads a task's name, and macOS's default file system a plist's file name, without regard to case, so a plan named `App` was another program's `app`: its install replaced it, and its removal deleted it.
- Security, Windows: `Install` makes the folder for a task's `task.xml` with the user as its owner and an access list, not inherited from the temp folder, that allows the user alone.
  - It reads the folder's access back by its handle and refuses the install when the file system did not keep it, as on FAT or exFAT.
  - It holds the folder by a handle that shares no delete until the folder is gone, makes `task.xml` through that handle with the same access, gives schtasks the path the handle names, and removes the file and the folder by their handles.
  - v0.4.0's folder took the temp folder's access, so another account that could modify, rename or redirect what the temp folder holds could swap in its own task between the write and schtasks' read. v0.4.0's note on this no longer applies.
  - Not held: an account that may rename or replace a folder above the temp folder, as schtasks reads the file by its path. See also the limits of this release, above.

### testenv

- Security: `Git` gives its git child `HOME` as the test's folder, which holds no `.netrc`. Without a `HOME`, libcurl took the home folder from the account and, for an http or https fetch or push, sent the password the person's `.netrc` holds for that host.
- Security: `Git` sets `GIT_SSH_COMMAND` to an ssh with no configuration file, no identity file, its known hosts in the test's folder and `BatchMode=yes`. ssh takes `~` from the account, not from `HOME`, so a test's git that reached an ssh remote read the person's `~/.ssh`: its config, `known_hosts` and keys. A test whose git needs a key names one in its own `GIT_SSH_COMMAND`.
- Changed: `GOTOOLCHAIN` is the caller's, as `GOWORK` is: it reaches a test only through `Keep`. A program that wants no toolchain download sets `GOTOOLCHAIN=local` and keeps it.
- Fixed: `NoLeaks` no longer passes a leak under load. It used to wait at most 10,000 yields for no goroutine to be running or runnable, so a leaked goroutine on a starved thread, or in a short runtime wait, passed as clean. It now waits until every other goroutine is blocked on a channel, a select, a `sync` lock, I/O, a sleep or a system call, yielding on one P. A run whose goroutines are still not blocked after the last yield returns 1 with every goroutine's stack.
- Fixed: `restore` removes a module cache a test's go filled beneath `Isolate`'s folder. go leaves a module cache's folders read-only, so on Unix `restore` failed and the `TestMain` panicked after every test passed. It now makes the folders beneath its own writable through an `os.Root` of the folder, so no link takes the change outside it, and removes them, as `go clean -modcache` does.

### gitenv

- Security: `Env` drops `NETRC`, in any case, beside the home names. libcurl 8.16 and later reads the file it names ahead of `HOME`'s `.netrc`, so a caller that set a `HOME` of its own still sent that file's password. A caller that wants a `.netrc` for its child adds `NETRC=<file>` in `add`.
- `Env` still leaves `HOME` and `GIT_SSH_COMMAND` to its caller. Its doc and README now say what that costs: a caller whose child reaches an http or https remote adds a `HOME` of its own, and one whose child reaches an ssh remote sets its own `GIT_SSH_COMMAND`, as `testenv.Git` does. Windows' libcurl finds a home only from the environment, which `Env` strips.

### For programs that import go-proc

- The module requires one new module, `github.com/containerd/cgroups/v3` v3.1.3, for `proc`'s cgroup on Linux. It brings in `github.com/cilium/ebpf`, `github.com/containerd/log`, `github.com/coreos/go-systemd/v22`, `github.com/godbus/dbus/v5`, `github.com/opencontainers/runtime-spec`, `github.com/sirupsen/logrus` and `google.golang.org/protobuf` as indirect requirements.
- go-proc's own lint refuses `github.com/stretchr/testify` and `gotest.tools` in its test files again, which v0.4.0 had lifted. `github.com/rogpeppe/go-internal/testscript` stays allowed, and `testify/mock` stays denied.

## v0.19.2 - 2026-11-28

No name is added, removed or moved, and no signature changes: the API check finds no break since v0.19.1. No promise in `api/contract.txt` changes, so this is a patch. What a name does changes in two places, each under Security below. On Linux, under glibc, `sandbox.RunHolding`, and `sandbox.Check` with folders, now pass over a folder in a list that glibc cannot walk, where v0.19.1 refused the program, and now refuse up front some programs that v0.19.1 ran, which breaks some callers. The Security entry names each refusal. Under musl nothing changes. On macOS, a run behind the block of `sandbox.Run` or `sandbox.RunHolding` no longer dies, now and then, before the system sandbox sets the profile. Of v0.19.1's list of loads not promised refused up front, the legacy subfolders of glibc up to 2.36 leave it, and one is left in the docs: a library found where a loader's search order differs from the search's in some other way. What the block enforces does not change. Nothing changes in `proc`, `service`, `load` or `gitenv`, and no require in go.mod changes. The tagged tree is 12,284 non-test Go lines outside `internal/` (`task size`), at its ceiling of 12,284, up 152 (1.3%) from v0.19.1's 12,132: 29 for the macOS wait and 123 for the glibc changes. The full release checks ran on macOS at the tagged commit; vet and the tests, with the race detector, ran on Linux, macOS and Windows at the tagged commit in CI. No full release checks ran on Linux or Windows for this release.

### For a v0.19.1 caller

On Linux, nothing changes for a program that does not call `sandbox.RunHolding`, or `sandbox.Check` with folders, or whose loader is musl. Under glibc, a program whose folder list holds a folder glibc cannot walk, such as a link loop, now runs when a later folder holds its library, where v0.19.1 refused it. Under glibc, a program is now also refused with `ErrUsage` before anything is set, whatever folders are named, when a library name the search looks for in a folder that is there is a link through a file. Under glibc 2.36 or older, or a glibc whose release cannot be told from its loader's file, it is refused as well when a folder the search looks in has a `tls/`, platform or hwcap subfolder beneath no built-in folder of its loader, and the error says when the release could not be told. Such a program runs only once its libraries are reached by the search order alone. On macOS, a run behind the block that died by SIGILL before the profile was set now runs, and a dry run whose exit no SIGCHLD says within the dry run's bound refuses the run with `ErrNoBlock` before the exec. Callers on Windows see no change.

### Security
* sandbox: on macOS, a run behind the block no longer dies, now and then, before the system sandbox sets the profile. The dry run's exit sends the caller SIGCHLD, and the exec of `sandbox-exec` followed the dry run's wait at once. A SIGCHLD still pending at the exec ended the new image at its first instruction with SIGILL, so the caller died in place of the program, in 12 of 30,000 starts under a load of four busy goroutines. It failed closed: nothing ran and no descriptor reached a program. The exec now waits until the runtime has taken a SIGCHLD sent since the dry run began. A dry run whose exit no SIGCHLD says within the dry run's bound refuses the run, matching `ErrNoBlock`, before the exec. The same 30,000 starts now all run. A SIGCHLD from another child of the caller, one that exits while the dry run runs or at the exec, is not held off.
* sandbox: on Linux, under glibc, the load search now passes over a folder in a list that glibc cannot walk, a link loop, a folder past the kernel's length limit or a file, and takes the next folder's library, as glibc does, where v0.19.1 refused the program. In a folder that is there, a path that the kernel answers with an error other than not found or permission denied is still refused, and so now is not a folder, a library name that is a link through a file: glibc up to 2.38 ends the folder list there, and 2.39 goes on, so for 2.39 the refusal fails closed. Under musl nothing changes: such a folder is still refused. Under glibc 2.36 or older, a folder the search looks in is now refused when its `tls`, platform or hwcap subfolder, which glibc up to 2.36 looks in first, has a real path beneath no built-in folder of the loader, is a link loop, or has a real path that cannot be told; a built-in folder's own still passes. The release is read from the loader's file, from the line its `--version` prints. Where the file names none, as before glibc 2.33, or names two that differ, the subfolder alone refuses the folder, and the error says so. Of v0.19.1's list of loads not promised refused up front, the legacy subfolders leave it. What the block enforces does not change. Breaking: a program under glibc 2.36 or older, or under a glibc whose release cannot be told, whose folder held has such a subfolder is now refused.

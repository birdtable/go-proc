## v0.14.0 - 2026-11-22

One name is added, in `gitenv`: `NoGlobalConfig`. No name is removed and no signature changes. Every name added is experimental, as every name of the module is. In `sandbox` a contract line and its tests are added, under Security below, and no product code changes; nothing changes in `proc`, `load` or `service`. go.mod is unchanged. The tagged tree is 10,521 non-test Go lines outside `internal/` (`task size`), at its ceiling of 10,521, up 12 from v0.13.0's 10,509, all for `NoGlobalConfig`.

### For a v0.13.0 caller

Nothing changes for a program that calls none of the new names: `Env`, `Repo`, `ReadArgs`, `Home`, `NoHome` and `CommitMode` give what they gave, `NoHome`'s add byte for byte, and no behaviour of the other packages moves. A caller that spelled `GIT_CONFIG_GLOBAL` itself, with `os.DevNull` (`NUL` on Windows), can take `NoGlobalConfig` instead.

### gitenv

- Added: `NoGlobalConfig()` is `GIT_CONFIG_GLOBAL=/dev/null` alone, the add of `Env` for a child that keeps a home but reads no global configuration, added after `Env`'s result and the caller's own add. It is `NoHome`'s second element byte for byte, and `NoHome` builds it from `NoGlobalConfig`, so a caller that held its own spelling, `os.DevNull` (`NUL` on Windows), takes go-proc's instead. `/dev/null` is the spelling on every system, which Git for Windows maps to its null device; git reads it from 2.32 on. The home stays the caller's, so libcurl still reads a `.netrc` there; `NoHome` is for a child that is to read neither. Its row runs on darwin, Linux and Windows: with a `.gitconfig` in `HOME`, a `git/config` in `XDG_CONFIG_HOME` and, on Windows, a `.gitconfig` in `USERPROFILE`, git reads none of them.

### Security

- sandbox: `api/contract.txt` promises, on every system, that a descriptor or handle the caller holds open when `Run` or `RunHolding` starts, made inheritable as a package init can (`syscall.Open` with no `O_CLOEXEC` on Linux and macOS, `bInheritHandle` true on Windows), never reaches the program, except the standard streams; on Windows neither starts a program. `TestWhatTheCallerHoldsInheritableAtRunNeverReachesTheProgram` holds it: on Linux and macOS a caller opens a file that way and the program finds no descriptor above stderr behind either call, where the same caller execing the program with no block hands it the file; on Windows both refuse with `ErrNoBlock` holding an inheritable handle and start nothing. It is the promise of what `Run` already did; no product code changes.

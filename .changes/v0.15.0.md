## v0.15.0 - 2026-11-22

One signature changes, in `sandbox`: `Check` changed from `func(Folders) (Block, error)` to `func(Folders, string) (Block, error)`. No name is added or removed. Before 1.0 a break is a minor version, so this tag is v0.15.0. Every name is experimental, as every name of the module is. Only `sandbox` changes, under Security and Fixed below; nothing changes in `proc`, `load`, `service` or `gitenv`. go.mod is unchanged. The tagged tree is 11,293 non-test Go lines outside `internal/` (`task size`), at its ceiling of 11,293, up 772 from v0.14.0's 10,521: 641 for the search of the folders a program loads from, 8 for the loader's floor and 123 for the macOS block's `posix_spawn`.

### For a v0.14.0 caller

- A caller of `Check` passes the program too: `sandbox.Check(f)` becomes `sandbox.Check(f, path)`, `path` being the program it will hand `RunHolding`. With no folders `path` is not read, so `Check(sandbox.Folders{}, "")` asks about `Run`.
- A caller of `RunHolding` stops naming the folders of the loader and the libraries in `ReadOnly` (`/usr/lib` and the like); `RunHolding` grants them itself. The program's own folder is still the caller's to name. A folder the caller goes on naming is held as it names it, and nothing is added over it.
- On Linux, a program whose load folders cannot be told, a `#!` script among them, is now refused with `ErrUsage` before anything is set, where before the block was set and the exec failed. For a script, the program to hand `RunHolding` is its interpreter.
- On macOS, a caller with goroutines that accept sockets, receive descriptors or call `dup` while the block is set should upgrade: see the first Security entry.

### Security

- sandbox, on macOS: the block no longer hands the program a socket another goroutine of the caller accepts while the block is set, a descriptor one receives in an `SCM_RIGHTS` message, or one from a raw `dup`. Every tag from v0.1.0 to v0.14.0 has this on darwin. It is the class v0.12.0's notes left open: Go on macOS marks an accepted socket or a received descriptor to close at exec in a second call, under no lock, and a raw `dup` not at all, so one made between the block's last marking and its exec reached the program whatever `syscall.ForkLock` held off. Measured on v0.12.0 on a Mac under `-race`, with goroutines doing nothing else, 76 of 900 programs held an accepted socket, 150 of 240 a received descriptor and 131 of 240 one from a raw `dup`. The block now starts `sandbox-exec` by `posix_spawn` with `POSIX_SPAWN_SETEXEC` and `POSIX_SPAWN_CLOEXEC_DEFAULT`, through libSystem with no cgo, so the kernel closes every descriptor but the standard streams, whatever its mark. A row for each of the three, and v0.12.0's pipe row, start the command 20 to 100 times under that load and find no descriptor above stderr in the program. The program still starts with the open-file limit the caller started with, not the one Go's runtime raised: `posix_spawn` does not put it back as `syscall.Exec` does, so the block first calls `syscall.Exec` with no path, which puts the limit back and fails with `ENOENT`, and any other answer refuses the run with `ErrNoBlock` with nothing set. That leans on a step of `syscall.Exec` no Go document promises: a Go that drops it gives the program the raised limit, and a macOS row pins the limit at two starting values. A failed spawn leaves the caller's limit at the one the process started with, as a failed `syscall.Exec` did. Linux is unchanged: Go marks those descriptors as it makes them there and the block execs by `execve`, but a descriptor from a raw `dup` after the last marking still reaches the program, so a Linux caller with such goroutines calls `Run` from a process that has none.
- sandbox: `RunHolding` grants, read-only and by itself on every call, the folders the program loads from, and `Check` takes the program, the breaking change above. On Linux `RunHolding` reads the program in the same call, just before it sets the block, and adds the real folder of the program's loader and of each library it and its libraries need, found by the loader's own search as it runs behind the block: glibc's and musl's rules for `DT_RPATH`, `DT_RUNPATH`, `$ORIGIN`, `$LIB`, `$PLATFORM` and the built-in folders, each file read by its program headers as the kernel and the loader read it, never by a section header. It does not read `/etc/ld.so.cache`, `/etc/ld.so.conf`, musl's path file, `LD_LIBRARY_PATH`, `LD_PRELOAD` or `LD_AUDIT`, and it never grants `/etc`. A program that names no loader adds none. `RunHolding`, and `Check` with folders, refuse with `ErrUsage`, naming the file, before anything is set: a `#!` script; a file that is not there, is not an ELF file or names two loaders; a loader that is neither glibc's nor musl's for the machine, or sits in a folder no layout has; a library the search does not find, or finds as a program (`ET_EXEC` or `DF_1_PIE`); a library whose real folder is the root or `/usr` itself, which is never granted; a `$` name the loader does not know; a search list entry that is empty or not an absolute path; and a search past 1024 libraries, 64 files from the program or 64 folders in one list. On macOS nothing is added, by measure: a program linked against libSystem starts with its own folder alone. Windows and FreeBSD read nothing and refuse as before.
- sandbox, on Linux: `RunHolding`, and `Check` with folders, refuse with `ErrUsage`, naming the file, a program whose loader's real folder, links resolved, is the root or `/usr` itself, as they refuse such a library. Without this, a musl loader the host's own links put there would have had its folder granted, and the grant would have been the whole tree or its system half. No tag had it: it closes a gap in the search before that search is first tagged. A glibc loader never reached it, as its folder is held to `/lib*` or `/usr/lib*`.

### Fixed

- sandbox: `TestWhatTheCallerHoldsInheritableAtRunNeverReachesTheProgram` no longer fails under `Run` in a container, or in any cgroup that has a `cpu.max`. The descriptor it found at 3 was the test program's own: a Go program's runtime opens its cgroup's `cpu.max` as it starts, to set GOMAXPROCS, and keeps it. The children the `sandbox/cmd/netblock` tests start now have `GODEBUG=containermaxprocs=0`, so the row's program opens no file of its own. `Run` and `RunHolding` are unchanged: in v0.14.0 nothing the caller held reached the program, and the row still fails when the marking of the caller's descriptors is taken out.

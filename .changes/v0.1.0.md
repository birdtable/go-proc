## v0.1.0 - 2026-11-15

The first release of go-proc. It runs other programs and tests safely: a run with a deadline, an output cap and a whole-tree kill on every system, a detached tree that can be stopped later, a sandbox that holds a run to given folders and to Unix sockets where the system allows it, one login service through the system's own tool, and clean environments for tests and for git. It needs Go 1.27 and, beside the standard library, `golang.org/x/sys` and `github.com/landlock-lsm/go-landlock`.

### Moved here

Four packages were first written in an earlier module of the same authors and are here whole. A program that used them there changes the import path (and for `sandbox` the package name); the names below under "Removed" are the only ones that do not come with them.

- `gitenv`: moved unchanged.
- `testenv`: moved unchanged.
- `sandbox`: the package was named `netblock`, and is renamed; its names (`Run`, `RunHolding`, `Folders`, `ErrNoBlock`, `ErrUsage`) are the same.
- `proc`: from an earlier private module that was never published, so no public import path changes.

`service` is new.

### Removed

- `proc.Start(dir, env, cmd)`, the old form. Use `proc.Run` to run a program to its end; `proc.Start` now takes a `Detached` and starts a tree that outlives the caller.
- `gitenv.Names`. `gitenv.Env` drops every `GIT_` name, and `gitenv.Repo` only the names that point at a repository.
- `testenv.Leaks`. Use the options `testenv.Keep` and `testenv.Drop` of `Main` and `Isolate`.

### proc

- `Run(ctx, Cmd)` runs the program at `Path`, each of `Args` one argument, with a `Timeout`, a `MaxOutput` for each stream and, on Unix, a `Grace` between SIGTERM and SIGKILL. The program runs in a tree of its own, a process group on Unix and a Job Object on Windows, and the whole tree is killed when the run ends. A nil `Env` means `Bare()`. A run it ended returns an `Ended` that says why.
- A `Cmd` it cannot bound is refused with an error wrapping `ErrRefused`, and the caller's program is never started. On Windows that includes a file that is not an `.exe` or `.com`. Every refusal comes before anything starts but one: on Linux a run held to `Limits.Memory` first starts this program again as the wrapper that sets the cap, and when the wrapper cannot set it, the run is refused after the wrapper ran and before the program did.
- `Path` is the program itself, never a name looked up in PATH. A relative `Path` must hold a separator (`./tool`, `bin/tool`) and is resolved against `Dir`, or against this process's folder when `Dir` is empty. A bare name is refused, and so on Windows are `C:tool.exe` and `\tool.exe`, which Windows resolves against a current folder instead of `Dir`. The other refusals of `Path` are under Security.
- `Start(Detached)` starts a program out of the caller's session, terminal and console, in a tree that outlives the caller, and returns a `Tree`: its `ID` is the `TreeID` that `Stop` takes, and its `Leader` is the started process. `Leader.Wait` reaps the leader, and the id names nothing from then on; a caller that exits without that wait leaves the reap to the system. `Stop(id)` kills that whole tree. An id whose leader is gone or reaped is `ErrStale`, and nothing is signalled. On Linux the id also carries the boot, the pid namespace and the time namespace, so an id kept across a reboot or used in another namespace is `ErrStale`. On macOS `Stop` checks the leader again before each kill after the first; once the leader is no longer the process the id names, it stops killing the group and goes on process by process, each checked the same way, and says when a process may run on because the group outlived its last pass. On FreeBSD and the other Unix systems `Start` and `Stop` refuse.
- `Cmd.Limits` holds a run to `Memory` bytes and `Processes` processes where the system can; a limit it cannot hold is refused by name, never weakened. On Linux, `Memory` needs `main` and `TestMain` to call `CappedExec(os.Args)` first and pass the result as `Cmd.Armed`, and a `Memory` above the caller's hard data limit (`RLIMIT_DATA`), or with that limit unreadable, is refused before anything starts.
- On Windows, `Usage(id)` reads a tree's CPU time, counting its processes that have ended as well as those still running, and its count of live processes; `Pids(id)` lists its processes; and `JoinTree()` puts this process in a tree of its own and returns its id, which `Usage`, `Pids` and `Stop` take. A tree whose leader has exited is `ErrStale` to `Usage` and `Pids`. On every other system each returns an error wrapping `errors.ErrUnsupported`.
- Fixed: when a tree cannot be killed, `Run` returns `Code` -1 without reading process state a later reap may still be writing. On Windows a job's settings no longer live in memory a moved goroutine stack can leave behind; under load a test once read the job as having no flags.

### Security

What hardens a run, in one place:

- proc: `Run` and `Start` refuse an empty `Path`, which names no program; a `Path` holding `=`, which env-style launchers read as a setting and do not run; and a `Path` beginning with `-`, which they read as an option. Name a program whose name begins with `-` as `./-name`.
- proc: on Linux, `Start` and `Stop` refuse where `/proc` is not this pid namespace's own, or gives no boot id or namespaces, or its `NSpid` line does not name this process alone (a mount of an outer pid namespace, or a kernel before Linux 4.1), since the check of a tree's leader would then read a different process from the one the kill reaches. Nothing is started or signalled, and the error matches `errors.ErrUnsupported`.
- proc: on Linux a run held to `Limits.Memory` is refused with `ErrRefused` where the kernel would take the limit and not hold it: below Linux 4.7, where `ignore_rlimit_data` does not read `N`, and where the kernel's release cannot be read as a version or that setting cannot be read. The error also matches `errors.ErrUnsupported`.

- sandbox: on Linux the seccomp filter that holds sockets to `AF_UNIX` is set on every thread of the process, or the run is refused with an error matching `ErrNoBlock`; a filter the kernel did not attach is never taken as set. Each run proves its own block: an `AF_INET` socket is made before the block as a control and must meet the filter's refusal behind it.

### sandbox

- On Linux the folder rules are a Landlock ruleset built by go-landlock. It needs Linux 6.12 or later on amd64 or arm64, with Landlock ABI 6 and its erratum 2; anywhere else on Linux the run is refused.
- On Linux every run needs an `AF_INET` socket before the block, as its probe's control. Where the host already refuses one, such as a systemd unit with `RestrictAddressFamilies=AF_UNIX` or a container profile without inet, every sandbox run is refused.
- `Check(Folders)` says whether `Run` or `RunHolding` could set the block, and sets nothing and starts nothing.

### service (new)

- `Install`, `Remove` and `Query` have the system's own tool take, drop or report one login service or timer whose files the caller writes: `systemctl --user` on Linux, `launchctl` in the login session on macOS and `schtasks` on Windows, run through the caller's `Runner`. Only the tools' machine-readable answers decide the result.
- A name of anything but ASCII letters, digits, `.`, `-` and `_`, or a file outside `Folders()`, is refused with `ErrUsage` before anything is written or run. On Windows a task holding a `%` is refused with `ErrPercent`. On other systems every call is `ErrAbsent`.

### testenv

- `Main` and `Isolate` take options: `Keep(names...)` lets a variable through the allow list and `Drop(prefixes...)` removes a prefix. Calls with no options compile as before.
- `Build(pkg, opts...)` builds a program under test once and returns a `*Binary`, whose `Run` and `RunInput` methods run it. `Environ` and `Lookup` read the environment `Main` made, in place of `os.Environ` and `os.LookupEnv`.
- Fixed: on Windows, `Isolate` also points `USERPROFILE`, `LOCALAPPDATA` and `APPDATA` at its own folders, so a test cannot reach the Windows home and settings of the person running it.

### gitenv

- `Repo(environ, add...)` is the environment without the variables that name a repository, keeping the author and the rest, for a git child that writes. `Without(environ, prefixes...)` drops the names that start with a prefix. A test holds the list of repository names to what `git rev-parse --local-env-vars` prints.

### For people working on go-proc

Nothing here changes what a caller sees.

- `API.txt` lists every exported name, and the pre-push check fails when it and the source differ.
- go-proc has its own Taskfile, lint and release settings, with every tool pinned in `tools/`. The `pre-commit`, `pre-push` and `release` tiers run their checks side by side, each with a timeout, and fail past their budgets in `budgets.yaml` (2, 10 and 15 seconds). The `secrets` check fails where git reads no history of the tree's own.
- `sandbox` makes its openat2 call through `golang.org/x/sys/unix` instead of a raw system call.
- The GitHub release workflow runs only by hand, runs the release tier on Linux and Windows, and creates the release only when both pass.
- The tests of `gitenv`, `sandbox` and `proc` run under `testenv.Main`, and each package fails when its `TestMain` stops calling it. On Windows every process a test starts is in a job the test binary holds open, so none outlives a killed run.

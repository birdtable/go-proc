## v0.6.0 - 2026-11-19

Three names are added, all in `proc`: `ChildrenCPU`, `Holds` and `ErrNotHeld`. None is removed, none is moved, and no signature changes. go.mod requires the same modules at the same versions as v0.5.0. The tagged tree is 10,563 non-test Go lines outside `internal/` (`task size`), at its ceiling of 10,563.

### For a v0.5.0 caller

Nothing breaks at build time. Four things change what a `proc` run returns:

- A `Cmd` that holds a NUL byte, in its `Path`, an argument, a variable of `Env`, its `Dir`, or the name of its `File`, is refused before anything starts, on every system, wrapping `ErrRefused` alone. Before, Linux refused some of these only at the start, and a `Limits.Contained` one read as a host that cannot hold the run.
- On Linux, a `Limits.Contained` run that fails for its own `Cmd` (a `Dir` that names no folder, a `Path` that names no program) is refused as the caller's own error, wrapping `ErrRefused` alone, and no longer matches `errors.ErrUnsupported`. A `Dir` that names no folder is now refused before the start. A start that fails with an errno other than `EPERM`, `EINVAL`, `ENOSPC` or `ENOSYS` is now refused as the run's own too, wrapping `ErrRefused` alone, the host's own refusals included, as `EACCES` from a security module that refuses the user namespace: in v0.5.0 every failed `Contained` start matched `errors.ErrUnsupported`, and now only those four do, so on such a host a caller that dropped `Contained` on `errors.ErrUnsupported` meets a hard refusal and keeps its limits. A caller that drops `Contained` when the host cannot hold it should test `ErrNotHeld`, below, so it never drops it over a mistyped path or a file the contained program put there.
- A run whose context has already ended starts nothing and ends with `WhyCancelled` and the context's cause, where it returned exec's bare context error.
- A run its context cuts while it runs, where the cause is itself an `Ended` (as another run's `WhyCap` error that `errgroup` gives its context), ends with `WhyCancelled` and that cause. On Unix it ended as the program's exit by the kill's signal, and on Windows with code 1 and no error.

### Refusals a caller now meets

Each is made before any program starts, unless it says otherwise.

- `proc`, every system, wrapping `ErrRefused` alone: a NUL byte in the `Cmd`, above.
- `proc` on Linux, wrapping `ErrRefused` alone, with `Limits.Contained`: a `Dir` that names no folder; a folder, the `Dir` or the caller's own, that the shim cannot find again by its path (one in a cgroup mount, one removed, one below a folder the caller's user cannot search); a directory handed to the program as its `Stdin` or among its `ExtraFiles`; a descriptor whose `fstat` fails.
- `proc` on Linux, wrapping `ErrRefused` and `errors.ErrUnsupported` and matching `ErrNotHeld`, with `Limits.Contained`: a shim that cannot mount the program's own cgroup v2 over each cgroup mount, as in a root that is not a mount point.
- `proc` on Linux, wrapping `ErrRefused` alone, at the start, with `Limits.Contained`: a start that fails with an errno other than `EPERM`, `EINVAL`, `ENOSPC` or `ENOSYS`, as `EACCES` from a security module that refuses the user namespace. Nothing of the program runs.
- `proc` on Linux, wrapping `ErrRefused`, after the start: a `Contained` run whose shim ended before its last step, or was skipped. With a skipped shim the program ran to its end without the hold, and its output is not given.

### proc

- Added: `Holds(c)` asks, before a run, whether this system can hold `c` here. It runs `Run`'s own checks on `c`, starts nothing and writes nothing, and returns the refusal `Run` would, or the `PeakKind` a run of `c` reads. `Run`'s refusal stays the authority: on Linux, `Holds` cannot try the write that gives the run's cgroup its memory controller, nor a `Contained` run's shim, so a `Holds` with no refusal does not promise a run.
- Added: `ErrNotHeld` is matched by each refusal of what this system cannot hold here: a `Limits` field, a `Grace`, a zero `Drain`, a `File` run, and a `TreeMemory` or `ReadPeak` from within a run's cgroup. A caller tells these from a `Cmd` of its own that is wrong without matching text. Each keeps its text and still wraps `ErrRefused` and `errors.ErrUnsupported`. A refusal that carries a system's errno (`ENOSYS`, `ENOTSUP`, `EOPNOTSUPP`) may match `errors.ErrUnsupported` and not `ErrNotHeld`.
- Added: `ChildrenCPU()` reads the CPU time, user and system, of this process's children that have ended and been waited for, by `getrusage(RUSAGE_CHILDREN)` on Unix. A child still running or not yet waited for is not in it, nor is a grandchild its parent did not wait for. On Windows, which keeps no such sum, it is an error wrapping `errors.ErrUnsupported`; there `TreeUsage.CPU` from `Usage` of the id `JoinTree` gives counts every process this one starts from then on, and includes this process's own CPU time, which `ChildrenCPU` does not.
- Changed: the NUL refusal, the `Contained` refusals and the ended-context results, above.
- Security, Linux: a `Limits.Contained` program can no longer freeze or kill its caller's cgroup and then take the memory controller from its own, running on with no limit and nothing to kill it. The shim now makes the program's mounts private, mounts a cgroup v2 rooted at the run's cgroup over each cgroup mount, finds its folder again through them, and closes at the exec every descriptor of the caller's that the run does not hand on. So no path the program can open names the caller's cgroup, its parent's or another run's.
  - Not held: a caller that hands the program an open file of another cgroup, or a host that shows it a proc mount of an outer pid namespace, still lets it reach one.
- Security, Linux: a `Contained` run whose shim ends before its steps is refused, not read as the program's exit. An `init` function of the caller's binary that runs before go-proc's, on a variable the shim's empty environment lacks, could end the shim with an exit code the caller then read as the program's. The shim now writes a ready byte just before its exec, and a run without it is refused, as is a start that skips the shim.
  - Not held: a program started without the shim inherits the descriptor the ready byte goes to, so it can write the byte itself.
  - A `TreeMemory` below the shim's own memory still ends the run with `WhyLimit`, and a `Timeout` or a context that ends before the shim is ready with `WhyDeadline` or `WhyCancelled`.
- Doc, Linux: `Limits.Contained` and the README no longer say a `Contained` program may take a caller's descriptors by `pidfd_getfd`. The kernel refuses that from a user namespace below the caller's, whatever Yama's setting.
- README: a shell in a scope systemd did not delegate, as a tmux scope under the user manager's `app.slice`, is refused `TreeMemory`. The README says why, and that the program runs as a delegated service instead.

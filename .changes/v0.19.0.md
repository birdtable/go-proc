## v0.19.0 - 2026-11-27

No name is added, removed or moved, and no signature changes: the API check finds no break since v0.18.0. What a name does changes in one place: on Linux, `sandbox.RunHolding`, and `sandbox.Check` with folders, refuse a library that lies outside both the caller's folders and its loader's built-in folders, which breaks some callers (under Security below). One promise in `api/contract.txt` changes, as `api/breaks/v0.18.0.contract.txt` records: on Linux the folders `RunHolding` adds no longer take such a library's folder, which is refused instead. One promise is added, in `sandbox`, on Linux, for that refusal. v0.18.0's known limit, under which such a library's folder was added, is gone, and the docs no longer name it. On macOS a new test shows that a program behind `RunHolding`'s block cannot link, clone, rename or swap a file or folder from outside the folders into a read-write one; no macOS code changes. Nothing changes in `proc`, `service`, `load` or `gitenv`, and no require in go.mod changes. The tagged tree is 12,037 non-test Go lines outside `internal/` (`task size`), at its ceiling of 12,037, up 56 (0.5%) from v0.18.0's 11,981, all for refusing such a library. The full release checks ran on macOS at the tagged commit; vet and the tests, with the race detector, ran on Linux, macOS and Windows at the tagged commit in CI. No full release checks ran on Linux or Windows for this release.

### For a v0.18.0 caller

Nothing changes for a program that does not call `sandbox.RunHolding`, or `sandbox.Check` with folders, on Linux. There, a program that loads a library, or loads a library that loads one, whose real file lies in a folder beneath neither a folder named in `Folders` nor a built-in folder of its loader is now refused with `ErrUsage` before anything is set, and the error names the library's file and its folder. Name that folder, or one above it, in `Folders` if you mean the program to load from it. A library beneath a built-in folder still loads with no folder named. Callers on macOS and Windows see no change.

### Security
* sandbox: on Linux, `RunHolding` and `Check` with folders refuse with `ErrUsage`, before anything is set, a library whose real file lies in a folder beneath neither a folder the caller named nor a built-in folder of the program's loader (glibc's, by the loader's real folder: in its architecture's lib folder, `/lib/<multiarch>`, `/usr/lib/<multiarch>`, `/lib` and `/usr/lib`; in `lib64`, `/lib64` and `/usr/lib64`; in `lib`, `/lib` and `/usr/lib`; musl's `/lib`, `/usr/local/lib` and `/usr/lib`), naming the file and its folder. That covers a library named by its full path, found by its run path, needed by another library, or reached through a symbolic link: each is judged by its real file, and each library by its own needs and run path. Before, such a library added its real folder, and all beneath it, to what the program could read and run, so a program, or a library it loads, written into a read-write folder could read a folder the caller never named. That was v0.18.0's known limit, and it is gone. A library beneath a built-in folder, a private folder in `/usr/lib/<multiarch>` among them, still runs, its folder added read-only as before. Breaking: a program that ran only because such a library's folder was added now needs that folder, or one above it, named in `Folders`.

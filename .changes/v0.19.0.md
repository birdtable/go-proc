## v0.19.0 - 2026-11-27

No name is added, removed or moved, and no signature changes: the API check finds no break since v0.18.0. What a name does changes in one place: on Linux, `sandbox.RunHolding`, and `sandbox.Check` with folders, no longer add the folder of a library outside both the caller's folders and its loader's built-in folders, so such a library fails at load behind the block, and refuse up front such a library as their load search finds it, which breaks some callers (under Security below). One promise in `api/contract.txt` changes, as `api/breaks/v0.18.0.contract.txt` records: on Linux the folders `RunHolding` adds no longer take such a library's folder, which the search refuses instead, for the inputs its test names. Two promises are added, in `sandbox`, on Linux, for that refusal, for the inputs their tests name, not every way a loader can reach a file. v0.18.0's known limit, under which such a library's folder was added, is gone; the docs name instead the loads the refusal up front does not cover, which load only from the folders the block grants. On macOS a new test shows that a program behind `RunHolding`'s block cannot link, clone, rename or swap a file or folder from outside the folders into a read-write one; no macOS code changes. Nothing changes in `proc`, `service`, `load` or `gitenv`, and no require in go.mod changes. The tagged tree is 12,065 non-test Go lines outside `internal/` (`task size`), at its ceiling of 12,065, up 84 (0.7%) from v0.18.0's 11,981, all for refusing such a library. The full release checks ran on macOS at the tagged commit; vet and the tests, with the race detector, ran on Linux, macOS and Windows at the tagged commit in CI. No full release checks ran on Linux or Windows for this release.

### For a v0.18.0 caller

Nothing changes for a program that does not call `sandbox.RunHolding`, or `sandbox.Check` with folders, on Linux. There, a program that needs a library, by its full path, by a run path, or through a link in a built-in folder, that the load search finds in a folder beneath neither a folder named in `Folders` nor a built-in folder of its loader is now refused with `ErrUsage` before anything is set, and the error names the library's file and its folder. Name that folder, or one above it, in `Folders` if you mean the program to load from it. A library the loader reaches another way is not promised refused up front: it loads only from the folders the block grants, and from anywhere else fails at load. A library beneath a built-in folder still loads with no folder named. Callers on macOS and Windows see no change.

### Security
* sandbox: on Linux, a program behind `RunHolding`'s block reads and runs only beneath the caller's folders, its loader's folder, and the real folders of the libraries the load search vouched for, each beneath a folder the caller named or a built-in folder of the program's loader (glibc's, by the loader's real folder: in its architecture's lib folder, `/lib/<multiarch>`, `/usr/lib/<multiarch>`, `/lib` and `/usr/lib`; in `lib64`, `/lib64` and `/usr/lib64`; in `lib`, `/lib` and `/usr/lib`; musl's `/lib`, `/usr/local/lib` and `/usr/lib`). A library anywhere else fails at load, with nothing granted for it. That is what the block enforces. Before, the search added a library's real folder, and all beneath it, wherever it lay, so a program, or a library it loads, written into a read-write folder could read a folder the caller never named. That was v0.18.0's known limit, and it is gone. Apart from that, `RunHolding` and `Check` with folders refuse with `ErrUsage`, before anything is set, a library outside the caller's folders and the loader's built-in folders as the search finds it, naming the file and its folder: each library the program or a library it loads needs, by its own needs and run path, by its full path, by a run path, or through a link in a built-in folder, judged by its real file, a symbolic link followed. The search imitates two loaders' search orders, so it refuses up front what it finds, not every way a loader can reach a file. A library the loader reaches another way is not promised refused up front, and loads only from the folders the block grants: one named by an audit or filter tag (DT_AUDIT, DT_DEPAUDIT, DT_FILTER or DT_AUXILIARY), one in a glibc-hwcaps subfolder, and one found where a loader's search order differs from the search's. A library beneath a built-in folder, a private folder in `/usr/lib/<multiarch>` among them, still runs, its folder added read-only as before. Breaking: a program that ran only because such a library's folder was added now needs that folder, or one above it, named in `Folders`.

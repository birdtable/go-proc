## v0.7.0 - 2026-11-19

Two names are added, both fields of `proc.Cmd`: `Stdout` and `Stderr`. `API.txt` adds two lines, `field proc.Cmd.Stderr io.Writer` and `field proc.Cmd.Stdout io.Writer`, both experimental. None is removed, none is moved, and no signature changes. go.mod requires the same modules at the same versions as v0.6.0. The tagged tree is 10,734 non-test Go lines outside `internal/` (`task size`), at its ceiling of 10,734.

### For a v0.6.0 caller

Nothing changes. A `Cmd` whose `Stdout` and `Stderr` are nil runs as it did in v0.6.0, and `Result` holds the same output.

### proc

- Added: `Cmd.Stdout` and `Cmd.Stderr`, each an `io.Writer`, are given the program's output while it runs, one writer for each stream. A writer gets exactly the bytes `Result` keeps of its stream, in order, so when `Run` returns, what it was given equals `Result.Stdout` or `Result.Stderr`, cut at `MaxOutput`, with the bytes read after a kill included. One writer may take both streams, and then gets their bytes in the order `Run` read them.
- How `Run` calls a writer: from a goroutine of its own, never with two `Write` calls at once, and never after `Run` returns. The bytes come as `Run` reads them, not split at line ends: lines are the caller's to find.
- What a slow writer costs: no read of the output waits for it, so `Timeout`, the `MaxOutput` cap, the kill of the program's tree and `Drain` work as before. Past them, `Run` waits for the `Write` in flight and one `Write` more, which carries what queued meanwhile. A `Write` that never returns holds `Run` as long, past the end of its context too. While a writer lags, the bytes it has not yet been given are held for it, up to `MaxOutput` for each stream, beside `Result`'s own copy.
- When a writer fails: a writer whose `Write` returns an error, writes fewer bytes than it was given with no error (`io.ErrShortWrite`), or ends its goroutine by `runtime.Goexit` is given no more. The run goes on, `Result` still holds all the output kept, and `Run`'s error wraps the writer's error and names the stream; for one writer of both streams, it names the streams the failed `Write` carried. A `Write` that panics is given no more either; `proc` does not recover the panic, which ends the process with the writer's own value, as a panic in any goroutine does.
- What a writer is not: it is this process's, and is never handed to the program, so `Limits.Contained`'s check of the descriptors a run hands on does not see it. A run refused after its start, as a `Limits.Contained` run whose shim never said it was ready, gives a writer nothing. `Start` takes no writer.

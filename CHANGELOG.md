## v0.16.0 - 2026-11-25

One function is added, in `proc`: `HoldsTreeMemory`, with its result type `TreeMemoryHold` and that type's three values. No name is removed or moved, and no signature changes: the API check finds no break since v0.15.0. Every name added is experimental, as every name of the module is. Nothing changes in `sandbox`, `service`, `gitenv` or `load`. In go.mod, go-testkit moves from v0.2.0 to v0.3.1, its public tag, for go-proc's own tests and `gitenv/gittest` alone; no other require changes. One fix, in `proc` on Windows, is under Security below. The tagged tree is 11,383 non-test Go lines outside `internal/` (`task size`), at its ceiling of 11,383, up 90 from v0.15.0's 11,293: 61 for `HoldsTreeMemory`, 23 for that fix and 6 of doc comments. The release checks ran on macOS (arm64), Linux (amd64) and Windows (amd64).

### For a v0.15.0 caller

Nothing changes for a program that does not call `HoldsTreeMemory`, but for `Stop` and `Interrupt` on Windows: every other name gives what it gave. On Windows, `Stop` and `Interrupt` of a tree whose leader has exited and been reaped are `ErrStale`, as they are documented to be and are on Linux and macOS, where before they could still end the processes the tree left running (see Security). A caller that asked `Holds` twice to learn whether a memory cap is held, once with the cap and once without it, can make one call to `HoldsTreeMemory` instead.

### Added

* proc: `HoldsTreeMemory(c Cmd) (TreeMemoryHold, PeakKind, error)` says how this system holds `c`'s `Limits.TreeMemory`, without starting anything. `TreeMemoryHeld` means the system holds the cap, and the `PeakKind` says how the peak is read. `TreeMemoryJudgedAfter` means the system cannot hold the cap but can read the run's peak, a tree's charge on Linux or one process's peak on macOS and the BSDs, so the caller can judge the cap by it after the run. `TreeMemoryRefused` means neither. A refusal for any other reason comes back as `Run` would give it, and a `c` with no `TreeMemory` comes back with a refusal of its own. `Contained` is kept as given, so a `Contained` `c` whose cap is not held is refused, never judged after.

### Changed

* build: go.mod requires `github.com/birdtable/go-testkit` v0.3.1, the public tag of its repository, where it required v0.2.0. Only go-proc's own tests and `gitenv/gittest`, a package for tests, import it, so a program that imports neither links none of it. Nothing in go-proc's API changes with it: v0.3.1 is v0.3.0 with its docs and its own gate changed, and adds, removes or moves no name. The API check, `task api`, is go-testkit's at that version, and `Taskfile.yml` calls Go programs in place of shell pipes. No exported name and no behaviour of the library changes.
* docs: the README is one page: what go-proc is for, how to install it, a quick start the tests compile and run, what each package is built on and adds, the systems and what each refuses, and how to report an issue. Each package README has the same shape, and the full reference is in the doc comments on pkg.go.dev. `SECURITY.md` says how to report a vulnerability privately, and `CONTRIBUTING.md` how to run the tests and send a change.
* docs: on Windows, a tree's id works only in the Windows session that started the tree. Used from another session, such as a service, a scheduled task that runs while you are logged off, or an ssh login, it gives `ErrStale` while the tree keeps running; `TreeID` and `ErrStale` now say so. Any process running as your user, in the tree or not, can keep a reaped leader's id working by holding the tree's job open, so the package doc and `ErrStale` now say "a process of the caller's user", not "a process of the tree", and `Stop` says what holding an id proves on Windows. The README no longer lists a zero `Drain` among what Windows refuses, since a zero `Drain` is `DefaultDrain` on every system, and it says the v0.16.0 release checks ran on all three systems.

### Security

* proc, on Windows: `Start` gave a tree's leader its handle of the Job Object as an inheritable duplicate in the caller's process, open from before the leader started until after it was resumed. A process another goroutine of the caller started meanwhile with every inheritable handle handed on, as `CreateProcess` outside `os/exec` may, took that handle too and kept the job named after the leader was reaped. `Stop` by the old id then ended the processes the tree had left running, and `Interrupt` answered the tree as live with `errors.ErrUnsupported`, both where `ErrStale` is documented. The handle is now duplicated straight into the suspended leader, not inheritable, so the caller never holds an inheritable handle of the job, and an id is stale once its leader is reaped. The leader's own children no longer inherit the handle either, so a tree whose leader exits while its children run is `ErrStale` to `Stop` and `Interrupt`, as the contract and Linux and macOS have it. Linux and macOS do not change, and no exported name changes.

### For a v0.14.0 caller

- A caller of `Check` passes the program too: `sandbox.Check(f)` becomes `sandbox.Check(f, path)`, `path` being the program it will hand `RunHolding`. With no folders `path` is not read, so `Check(sandbox.Folders{}, "")` asks about `Run`.
- A caller of `RunHolding` stops naming the folders of the loader and the libraries in `ReadOnly` (`/usr/lib` and the like); `RunHolding` grants them itself. The program's own folder is still the caller's to name. A folder the caller goes on naming is held as it names it, and nothing is added over it.
- On Linux, a program whose load folders cannot be told, a `#!` script among them, is now refused with `ErrUsage` before anything is set, where before the block was set and the exec failed. For a script, the program to hand `RunHolding` is its interpreter.
- On macOS, a caller with goroutines that accept sockets, receive descriptors or call `dup` while the block is set should upgrade: see the first Security entry.

### Security

- sandbox, on macOS: the block no longer hands the program a socket another goroutine of the caller accepts while the block is set, a descriptor one receives in an `SCM_RIGHTS` message, or one from a raw `dup`. Every tag from v0.1.0 to v0.14.0 has this on darwin. It is the class v0.12.0's notes left open: Go on macOS marks an accepted socket or a received descriptor to close at exec in a second call, under no lock, and a raw `dup` not at all, so one made between the block's last marking and its exec reached the program whatever `syscall.ForkLock` held off. Measured on v0.12.0 on a Mac under `-race`, with goroutines doing nothing else, 76 of 900 programs held an accepted socket, 150 of 240 a received descriptor and 131 of 240 one from a raw `dup`. The block now starts `sandbox-exec` by `posix_spawn` with `POSIX_SPAWN_SETEXEC` and `POSIX_SPAWN_CLOEXEC_DEFAULT`, through libSystem with no cgo, so the kernel closes every descriptor but the standard streams, whatever its mark. A row for each of the three, and v0.12.0's pipe row, start the command 20 to 100 times under that load and find no descriptor above stderr in the program. The program still starts with the open-file limit the caller started with, not the one Go's runtime raised: `posix_spawn` does not put it back as `syscall.Exec` does, so the block first calls `syscall.Exec` with no path, which puts the limit back and fails with `ENOENT`, and any other answer refuses the run with `ErrNoBlock` with nothing set. That leans on a step of `syscall.Exec` no Go document promises: a Go that drops it gives the program the raised limit, and a macOS row pins the limit at two starting values. A failed spawn leaves the caller's limit at the one the process started with, as a failed `syscall.Exec` did. Linux is unchanged: Go marks those descriptors as it makes them there and the block execs by `execve`, but a descriptor from a raw `dup` after the last marking still reaches the program, so a Linux caller with such goroutines calls `Run` from a process that has none.
- sandbox: `RunHolding` grants, read-only and by itself on every call, the folders the program loads from, and `Check` takes the program, the breaking change above. On Linux `RunHolding` reads the program in the same call, just before it sets the block, and adds the real folder of the program's loader and of each library it and its libraries need, found by the loader's own search as it runs behind the block: glibc's and musl's rules for `DT_RPATH`, `DT_RUNPATH`, `$ORIGIN`, `$LIB`, `$PLATFORM` and the built-in folders, each file read by its program headers as the kernel and the loader read it, never by a section header. It does not read `/etc/ld.so.cache`, `/etc/ld.so.conf`, musl's path file, `LD_LIBRARY_PATH`, `LD_PRELOAD` or `LD_AUDIT`, and it never grants `/etc`. A program that names no loader adds none. `RunHolding`, and `Check` with folders, refuse with `ErrUsage`, naming the file, before anything is set: a `#!` script; a file that is not there, is not an ELF file or names two loaders; a loader that is neither glibc's nor musl's for the machine, or sits in a folder no layout has; a library the search does not find, or finds as a program (`ET_EXEC` or `DF_1_PIE`); a library whose real folder is the root or `/usr` itself, which is never granted; a `$` name the loader does not know; a search list entry that is empty or not an absolute path; and a search past 1024 libraries, 64 files from the program or 64 folders in one list. On macOS nothing is added, by measure: a program linked against libSystem starts with its own folder alone. Windows and FreeBSD read nothing and refuse as before.
- sandbox, on Linux: `RunHolding`, and `Check` with folders, refuse with `ErrUsage`, naming the file, a program whose loader's real folder, links resolved, is the root or `/usr` itself, as they refuse such a library. Without this, a musl loader the host's own links put there would have had its folder granted, and the grant would have been the whole tree or its system half. No tag had it: it closes a gap in the search before that search is first tagged. A glibc loader never reached it, as its folder is held to `/lib*` or `/usr/lib*`.

### Fixed

- sandbox: `TestWhatTheCallerHoldsInheritableAtRunNeverReachesTheProgram` no longer fails under `Run` in a container, or in any cgroup that has a `cpu.max`. The descriptor it found at 3 was the test program's own: a Go program's runtime opens its cgroup's `cpu.max` as it starts, to set GOMAXPROCS, and keeps it. The children the `sandbox/cmd/netblock` tests start now have `GODEBUG=containermaxprocs=0`, so the row's program opens no file of its own. `Run` and `RunHolding` are unchanged: in v0.14.0 nothing the caller held reached the program, and the row still fails when the marking of the caller's descriptors is taken out.

### Security

All but the last are in `proc`, about a `Limits.Contained` run on Linux; the last is in `sandbox`, on macOS.

- The covers the shim puts over the cgroup mounts are now read back when the run's report says ready (v0.8.0 said they were not). The caller freezes the run's cgroup, reads each of its threads, and each cgroup below it, for the cover by mount id and parent id, with the cover's root at the run's cgroup as the caller sees it, and thaws it after. So a program that skipped the shim, dropped its capabilities, set `no_new_privs` itself before it wrote the ready byte and left a cgroup mount open is refused, and its tree is killed. A task that is ending counts as gone; a thread-group leader that ended alone is gone for itself, and its other threads are read; a cgroup that can't be frozen refuses the run. The shim now ends in a second stage: the caller's binary started again once `no_new_privs` is set and no capability is left, so every thread the caller reads began with neither. That stage starts the program only when the caller, its check passed, tells it to, so the check never reads a step of the program's. What it does not see: a user namespace of the program's that rebuilds the cover's shape and root from the caller's mount; a descriptor on the caller's cgroup tree that a process of the same user outside the tree hands to the program after ready; a write before ready to a cgroup other than the run's, which survives the refusal and the kill; and a reference to the caller's cgroup mount that a start which skipped the shim keeps as a working directory, a root, a detached clone of a mount above it, or a descriptor in flight in a socket pair the tree holds. A second process of the same user, outside the run's cgroup namespace, can move a process of the run to another of the user's cgroups: it is charged there, so the run's memory limit does not hold for it while the move lasts, and the tree's kill still reaches it through the run's pid namespace. The charge of the caller's binary as the program starts is in the section for a v0.11.0 caller.
- The run is now refused, and its tree killed, where the check at ready finds a descriptor on a cgroup file system, of either version and wherever it is mounted, or on a mount namespace, in any thread of the run's cgroup. Each thread's own descriptors are read, so a thread with a file table of its own is read too, and the error names the thread, the descriptor's number and what it is on. A caller that hands such a descriptor to the run is refused, as one that hands a directory already was. A descriptor that a process outside the tree hands back after ready is not seen.
- The check of the run's limit now reads back every file the run wrote, not `memory.max` alone: `memory.swap.max` must read `0` and `memory.oom.group` `1`, or the run ends with an error naming the file and what it reads, and its tree is killed. A write before ready to a cgroup other than the run's still survives the refusal and the kill.
- The run is no longer refused as forged where the caller's cgroup mount root lies above its cgroup namespace's root, as for a caller that unshared a cgroup namespace without mounting cgroup2 again. The leading `..` parts of the mount root are now cancelled by as many leading parts of the path below the mount. A run that lies outside the caller's namespace, which the kernel does not let the caller place, is still refused.
- The shim asks for its ambient capability before it touches its report. A start that gives it none, as a setuid or file-capability exec of a binary that imports proc does, now exits 127 having written nothing and closed no descriptor, where before it wrote two fixed bytes to the descriptor its arguments named, which could be one an earlier `init` of that binary opened.
- The macOS block no longer hands the program a descriptor another goroutine of the caller holds open as the block is set, nor a pipe or a new socket one makes then. This affects `sandbox` on darwin only, in every tag from v0.1.0 to v0.11.0; a darwin caller should upgrade to v0.12.0. The block found the descriptors to mark by listing /dev/fd with `os.ReadDir`, which stats each entry and leaves out one whose stat says EBADF; while other goroutines look up /dev/fd at once, that stat now and then says EBADF of a descriptor held open, so one could stay unmarked and reach the sandboxed program. The listing is now read by its names alone, which stats nothing. And macOS makes a pipe or a socket and marks it in two calls, so one another goroutine made between the last marking and the exec could reach the program too; the block now holds `syscall.ForkLock`, under which Go makes them, from that marking into the exec. One class stays, since the exec stops no other goroutine: any descriptor another goroutine makes or receives without `syscall.ForkLock` after the last marking can still reach the program, on macOS one from `Accept`, a received `SCM_RIGHTS` message or a raw `dup`, and on Linux, where Go marks the others as it makes them, a raw `dup`. A caller with such goroutines calls `Run` from a process that has none; `posix_spawn` on macOS, which closes the class in the kernel, is planned. Linux makes and marks a pipe or a socket in one call and marks by `close_range`, in every tag, and is not affected by either path.

### proc

- Added: `Cmd.Stdout` and `Cmd.Stderr`, each an `io.Writer`, are given the program's output while it runs, one writer for each stream. One writer may take both streams, and then gets their bytes in the order `Run` read them.

While a writer lags, the bytes it has not yet been given are held for it, up to `MaxOutput` for each stream, beside `Result`'s own copy.
- When a writer fails: a writer whose `Write` returns an error, writes fewer bytes than it was given with no error (`io.ErrShortWrite`), or ends its goroutine by `runtime.Goexit` is given no more. The run goes on, `Result` still holds all the output kept, and `Run`'s error wraps the writer's error and names the stream; for one writer of both streams, it names the streams the failed `Write` carried. A `Write` that panics is given no more either; `proc` does not recover the panic, which ends the process with the writer's own value, as a panic in any goroutine does.
- What a writer is not: it is this process's, and is never handed to the program, so `Limits.Contained`'s check of the descriptors a run hands on does not see it. A run refused after its start, as a `Limits.Contained` run whose shim never said it was ready, gives a writer nothing. `Start` takes no writer.

Nothing breaks at build time. Four things change what a `proc` run returns:

- A `Cmd` that holds a NUL byte, in its `Path`, an argument, a variable of `Env`, its `Dir`, or the name of its `File`, is refused before anything starts, on every system, wrapping `ErrRefused` alone. Before, Linux refused some of these only at the start, and a `Limits.Contained` one read as a host that cannot hold the run.
- On Linux, a `Limits.Contained` run that fails for its own `Cmd` (a `Dir` that names no folder, a `Path` that names no program) is refused as the caller's own error, wrapping `ErrRefused` alone, and no longer matches `errors.ErrUnsupported`. A `Dir` that names no folder is now refused before the start. A start that fails with an errno other than `EPERM`, `EINVAL`, `ENOSPC` or `ENOSYS` is now refused as the run's own too, wrapping `ErrRefused` alone, the host's own refusals included, as `EACCES` from a security module that refuses the user namespace: in v0.5.0 every failed `Contained` start matched `errors.ErrUnsupported`, and now only those four do, so on such a host a caller that dropped `Contained` on `errors.ErrUnsupported` meets a hard refusal and keeps its limits. A caller that drops `Contained` when the host cannot hold it should test `ErrNotHeld`, below, so it never drops it over a mistyped path or a file the contained program put there.
- A run whose context has already ended starts nothing and ends with `WhyCancelled` and the context's cause, where it returned exec's bare context error.
- A run its context cuts while it runs, where the cause is itself an `Ended` (as another run's `WhyCap` error that `errgroup` gives its context), ends with `WhyCancelled` and that cause. On Unix it ended as the program's exit by the kill's signal, and on Windows with code 1 and no error.

### Refusals a caller now meets

Each is made before any program starts, unless it says otherwise.

- `proc`, every system, wrapping `ErrRefused` alone: a NUL byte in the `Cmd`, above.
- `proc` on Linux, wrapping `ErrRefused` alone, with `Limits.Contained`: a `Dir` that names no folder; a folder, the `Dir` or the caller's own, that the shim cannot find again by its path (one in a cgroup mount, one removed, one below a folder the caller's user cannot search); a directory handed to the program as its `Stdin` or among its `ExtraFiles`; a descriptor whose `fstat` fails.
- `proc` on Linux, wrapping `ErrRefused` and `errors.ErrUnsupported` and matching `ErrNotHeld`, with `Limits.Contained`: a shim that cannot mount the program's own cgroup v2 over each cgroup mount, as in a root that is not a mount point.
- `proc` on Linux, wrapping `ErrRefused` alone, at the start, with `Limits.Contained`: a start that fails with an errno other than `EPERM`, `EINVAL`, `ENOSPC` or `ENOSYS`, as `EACCES` from a security module that refuses the user namespace. Nothing of the program runs.
- `proc` on Linux, wrapping `ErrRefused`, after the start: a `Contained` run whose shim ended before its last step, or was skipped. With a skipped shim the program ran to its end without the hold, and its output is not given.

### proc

- Added: `Holds(c)` asks, before a run, whether this system can hold `c` here. It runs `Run`'s own checks on `c`, starts nothing and writes nothing, and returns the refusal `Run` would, or the `PeakKind` a run of `c` reads. `Run`'s refusal stays the authority: on Linux, `Holds` cannot try the write that gives the run's cgroup its memory controller, nor a `Contained` run's shim, so a `Holds` with no refusal does not promise a run.
- Added: `ErrNotHeld` is matched by each refusal of what this system cannot hold here: a `Limits` field, a `Grace`, a zero `Drain`, a `File` run, and a `TreeMemory` or `ReadPeak` from within a run's cgroup. A caller tells these from a `Cmd` of its own that is wrong without matching text. Each keeps its text and still wraps `ErrRefused` and `errors.ErrUnsupported`. A refusal that carries a system's errno (`ENOSYS`, `ENOTSUP`, `EOPNOTSUPP`) may match `errors.ErrUnsupported` and not `ErrNotHeld`.
- Added: `ChildrenCPU()` reads the CPU time, user and system, of this process's children that have ended and been waited for, by `getrusage(RUSAGE_CHILDREN)` on Unix. A child still running or not yet waited for is not in it, nor is a grandchild its parent did not wait for. On Windows, which keeps no such sum, it is an error wrapping `errors.ErrUnsupported`; there `TreeUsage.CPU` from `Usage` of the id `JoinTree` gives counts every process this one starts from then on, and includes this process's own CPU time, which `ChildrenCPU` does not.
- Changed: the NUL refusal, the `Contained` refusals and the ended-context results, above.
- Security, Linux: a `Limits.Contained` program can no longer freeze or kill its caller's cgroup and then take the memory controller from its own, running on with no limit and nothing to kill it. The shim now makes the program's mounts private, mounts a cgroup v2 rooted at the run's cgroup over each cgroup mount, finds its folder again through them, and closes at the exec every descriptor of the caller's that the run does not hand on. So no path the program can open names the caller's cgroup, its parent's or another run's.
  - Not held: a caller that hands the program an open file of another cgroup, or a host that shows it a proc mount of an outer pid namespace, still lets it reach one.
- Security, Linux: a `Contained` run whose shim ends before its steps is refused, not read as the program's exit. An `init` function of the caller's binary that runs before go-proc's, on a variable the shim's empty environment lacks, could end the shim with an exit code the caller then read as the program's. The shim now writes a ready byte just before its exec, and a run without it is refused, as is a start that skips the shim.
  - Not held: a program started without the shim inherits the descriptor the ready byte goes to, so it can write the byte itself.
  - A `TreeMemory` below the shim's own memory still ends the run with `WhyLimit`, and a `Timeout` or a context that ends before the shim is ready with `WhyDeadline` or `WhyCancelled`.
- Doc, Linux: `Limits.Contained` and the README no longer say a `Contained` program may take a caller's descriptors by `pidfd_getfd`. The kernel refuses that from a user namespace below the caller's, whatever Yama's setting.
- README: a shell in a scope systemd did not delegate, as a tmux scope under the user manager's `app.slice`, is refused `TreeMemory`. The README says why, and that the program runs as a delegated service instead.

### Breaking for a v0.4.0 caller

- `proc` on Windows: a `Cmd.Grace` above zero is refused. Windows sends no TERM a program can catch, so the job's kill always ended the tree at once and the grace was no time given. A Windows caller sets `Grace: 0` there and keeps its own grace elsewhere.

The copy left out each line it could see a credential on, but a credential in `GOFLAGS`, in a `GOPROXY` or `GONOSUMDB` URL, in a `.netrc` that `GOPRIVATE` sends go to, or behind `GOAUTH` now reaches a test only through a name the test keeps.

### proc

- Added: `Limits.Contained`, on Linux, holds the run's tree to `Limits.TreeMemory` against a process of the tree that moves itself out of the run's cgroup or writes its limit.
  - The program starts in user, cgroup, pid and mount namespaces of its own. The cgroup namespace is rooted at the run's cgroup, and the user namespace maps the caller's uid and gid each to itself.
  - It starts through a shim: the caller's own binary, run again before `main`. The shim writes 0 to the namespace's `user.max_cgroup_namespaces`, mounts the tree's own proc on `/proc`, sets `no_new_privs`, drops every capability and execs the program.
  - The kernel then refuses a process of the tree that moves out of the run's cgroup or writes its `memory.max` or `memory.swap.max`, and the run kills the tree itself once the cgroup counts an oom.
  - The tree may still write `-memory` to the `cgroup.subtree_control` of the run's parent, which takes the memory controller and the limit from the run's cgroup. While the caller runs, the run then kills the tree, from one inotify watch, and ends with an error that names the loss, never `limit`. It does the same when the cgroup's `memory.max` reads other than it set, or its `memory.events` cannot be read.
  - It holds the run's own cgroup alone: the tree may still write the files of another cgroup of the caller's user, another run's or the caller's.
  - Not held: the two above together. Every kill on a lost limit, like `Timeout` and the kill at the run's end, is made by the running caller, and the tree gets no signal when the caller dies. So a tree that first freezes or kills the caller's cgroup, then writes `-memory` to the parent's `cgroup.subtree_control`, runs on with no limit, and nothing kills it.
  - What it costs the program: it can make no cgroup namespace of its own. It is pid 1, so it ignores `SIGTERM` without a handler, reaps its tree's orphans and ends the tree as it exits. Its `/proc` lists its own tree alone. It sees its cgroup as `/` and other users' ids as 65534. A setuid file or a file's capabilities give it nothing.
  - What it costs the caller: the shim's memory counts in `TreeMemory`, and the caller's other `init` functions run in the shim. The shim starts with no environment, so no loader variable of the run's `Env` reaches it, and it hands the program its `Env` through a descriptor.
  - It is refused where the kernel, a security module or a container refuses an unprivileged user namespace, the shim's write or its proc mount, with the error inside; where cgroup v2 is not mounted with `nsdelegate`; without `TreeMemory`; with `Terminal`, whose terminal the tree could type into; to a caller whose effective uid is 0, as the tree would keep uid 0 and could write the kernel's global settings; and on Windows, where a process of the tree may clear its job's limit.
  - The zero `Cmd` runs as before.
- Added: `Result.PeakKind` names what `Result.Peak` counts, one of a closed list of `PeakKind`: `PeakTreeCharged` (Linux, the cgroup's charge for the whole tree), `PeakProcessResident` (the BSDs and macOS, one process's resident set), `PeakProcessCommitted` (Windows, one process's committed memory), and `PeakNone` where `PeakRead` is false. `Limits.TreeMemory`'s doc names what each system's cap holds. `Peak` and `PeakRead` are as they were.
- Changed, Linux: `Limits.TreeMemory` and `Cmd.ReadPeak` use a cgroup of the run's own, made beside the caller's cgroup in the parent systemd delegated (`Delegate=yes` with `DelegateSubgroup=`; the README gives the `systemd-run` line). The program starts in it, with no wrapper.
  - `TreeMemory` is that cgroup's `memory.max`, with no swap. A tree that passes it is killed whole and the run ends `limit`.
  - Not held: hugetlb pages are not charged to `memory.max` unless cgroup v2 is mounted with `memory_hugetlb_accounting` (Linux 6.7). So where the host keeps a hugetlb pool, a tree may map such pages past `TreeMemory`, uncounted in `Peak`, with `Contained` or without.
  - It holds a program that leaves its cgroup alone. A process of the tree runs as the caller's user, so it may write the cgroup's files or move itself to another cgroup under the delegated one, and is then out of the limit; one that moves is out of the kill at the run's end, and of the peak.
  - The cgroup is ended by `cgroup.kill` and removed at the run's end, with any cgroup its tree made in it. So a process of the tree that left its process group, or started a session of its own, is ended with the run, with `ReadPeak` alone too.
- Changed, Linux: `Cmd.ExtraFiles` and `Cmd.File` are no longer refused with `ReadPeak`. v0.4.0's note that a run through the wrapper starts it from `/proc/self/exe` without checking `/proc` no longer applies, as no run starts one.
- Changed: on Unix, a pipe no process holds when `Drain` ends is read for what it held then, so a zero `Drain` keeps output a program left buffered. On Windows every read is bounded by `Drain`. `Run` returns within `Timeout`, `Grace` and `Drain`; it could return 10 s past `Timeout` and `Grace` before. A short `Drain` gives an `escaped` end to a run whose killed member has not yet exited, or whose pipe is held, from fork to exec, by a program this process starts at the same moment.
- Fixed, Linux: a `Limits.TreeMemory` run ends `limit` only when its own cgroup's `memory.max` killed the tree. A tree that met its limit, got `ENOMEM` where the oom killer found no process to kill and exited 0, ended `limit`, as did one whose own cgroup beneath the run's killed part of it. Each now ends as its exit says. What is killed is unchanged.
- Security, Linux: a `Limits.TreeMemory` or `Cmd.ReadPeak` run reads which cgroup this process is in from `/proc/self/cgroup` only once `/proc` is a folder, not a link, on a proc file system. In a root whose `/proc` was another folder, a planted `self/cgroup` chose the run's cgroup. There `TreeMemory` is now refused, and a run that only reads its peak goes with `PeakRead` false.
- Security, Linux: `Start` and `Stop` open `/proc` once, check that it is the root of a proc file system, and read every file below that one descriptor, so a mount on `/proc`, or a rename of its folder, after the check is not read.
  - In a root whose `/proc` was a planted folder, `Stop` of an id whose leader was gone read a planted stat as the leader's and sent `SIGKILL` to the group that held its number.
  - Where the kernel gives `openat2`, no read crosses a mount: a file bound below `/proc`, as over a live leader's stat, is refused, wrapping `syscall.EXDEV`, and nothing is signalled. Before Linux 5.6, or where a filter refuses `openat2`, each file opened must be on the proc mount's own file system, so one bound from another is refused the same way.
  - `/proc/sys` is read only on the proc mount's own file system, so a mount there cannot choose the boot `Start` and `Stop` read.
  - Not held: on the `openat` route, a file or folder of the same proc mount bound over another is read as the kernel's; and a file system whose server answers `statfs` as proc, with the root's inode, as 9p may, is taken for proc.
  - A `Run`'s check for a group left behind reads `/proc` under the same check.
- Security, macOS: `Result.Left` no longer reads false while a process of the tree runs on. For a moment, a process whose exec is finishing as its parent exits is in no listing of its group, and a kill of the group does not find it. About once in 2,000 runs under load, of a program that starts a worker and exits, `Left` read false with the worker running. The group is now listed before the stop as well as after it, and a process in either listing counts, so `Left` reads true a little more often.
- Security, macOS: a tree kill, at a run's end or by `Stop`, no longer ends as done while such a process still runs past its exec. After a `SIGKILL` of the group, each process a listing held is asked with a kill of 0, which waits out an exec, and read by the `kern.proc.pid` sysctl. While one is live in the group, the group is killed again; past the kill tries the end is an error that the group still holds a live process. Before, 3 in 120,000 runs under load ended as done with the worker running.
- Security, Windows: `Limits.TreeMemory`, `Limits.Processes` and the job's hold on the tree are now stated limits in the doc and the README. A process of the tree runs as the caller's user, at its integrity, so it may open the caller, duplicate the job's handle from it, and then clear either limit, allow breakaway and start a process out of the job, clear kill-on-close, or keep the job alive past the caller's end. A test row shows it. Holding a hostile program needs another token (Low integrity or an AppContainer), which is a sandbox's job, not proc's.

## v0.4.0 - 2026-11-18

Thirty-three names are added, two are removed with no alias, and none is moved. The removed names are both in `proc`: `proc.Cmd.NoTerminal`, whose place `proc.Cmd.Terminal` takes with the opposite default, and `proc.Limits.Memory`, whose place `proc.Limits.ProcessData` and `proc.Limits.TreeMemory` take. A new package, `load`, is added. `gitenv`'s names and behaviour do not change. The tagged tree is 9,869 non-test Go lines outside `internal/` (`task size`), under the ceiling of 9,870.

### Breaking for a v0.3.0 caller

- `proc`: the zero `Cmd` gives the program no terminal of the caller's.
  - `Cmd.NoTerminal` is removed and `Cmd.Terminal` takes its place, with no alias. A caller that set `NoTerminal: true` now sets nothing. A caller that relied on the program getting its terminal, or on Windows its console, sets `Terminal: true`.
  - So a zero `Cmd` whose `Stdin` is a terminal, a console, or the pipe of an MSYS or Cygwin pty is now refused, wrapping `ErrRefused`, as one with `NoTerminal` was. A run with `Terminal` asks nothing of its `Stdin`.
  - `Detached` is unchanged: it starts with no terminal, as before.
- `proc`: `Limits.Memory` is removed, with no alias. It held two different things: each process's data segment on Linux, and the memory the whole tree commits on Windows. A caller picks one of the two new fields: `Limits.ProcessData` on Linux, `Limits.TreeMemory` on Windows.
- `service` on Windows keeps no file of a task.
  - `Folders()` answers an empty list and no error there, and a Windows plan's one `File` leaves `Path` empty. A `Path` that is set is refused, wrapping `ErrUsage`.
  - `Install` writes the task's XML to `task.xml` in a new folder of the system's temp folder, has `schtasks /create` read it there, and removes the folder whether or not schtasks took the task. `Remove` deletes the task and no file.
  - A `go-proc\service\<name>.xml` that v0.3.0 wrote under the user's local application data is no longer read or removed, so the caller may delete it.
- `service`: `Plan.Name` refuses, on every system, a name that ends in `.` and a name whose part before its first `.` is a Windows device name, in any case: `CON`, `PRN`, `AUX`, `NUL`, `COM0` to `COM9`, `LPT0` to `LPT9`. v0.3.0 took them.
- `testenv`: `Main` no longer reads a `windows-skips.txt` at the module's root. A module that kept one passes its names to the new `SkipOnWindows`. The file was read before the tests ran, outside go test's cache key, so an edit to it replayed an old result.
- `testenv`: `Isolate` and `Main` no longer force `GOWORK=off`. A run's `GOWORK` passes or leaks as `Keep` and `Drop` say, like any other name, and with neither it leaks, so a test's go finds a workspace as go does. A module that wants none sets `GOWORK=off` before `Main` and passes `Keep("GOWORK")`. `GIT_CONFIG_NOSYSTEM=1` and go's telemetry off stay, as safe defaults of the isolation.

### Refusals a caller now meets

Each is made before any program starts, unless it says otherwise.

- `proc`, wrapping `ErrRefused`:
  - a zero `Cmd` whose `Stdin` is a terminal, a console or an MSYS or Cygwin pty's pipe (above);
  - a negative `Cmd.Drain`, and a `Drain`, its zero default included, that with `Grace` passes the longest `time.Duration`;
  - `Limits.TreeMemory` on any system but Windows, and `Limits.ProcessData` on any system but Linux, each wrapping `errors.ErrUnsupported` too;
  - an entry of `Cmd.ExtraFiles` that is nil or a closed file, on every system;
  - on Linux, `Cmd.ExtraFiles` with a run that starts through the wrapper (`ReadPeak` or `Limits.ProcessData`), since the wrapper takes descriptor 3 and on for itself;
  - a set `Cmd.File` on any system but Linux, wrapping `errors.ErrUnsupported` too;
  - on Linux, a `File` with `Path`, a `File` that begins with `#!` or whose start cannot be read, a `File` with a run through the wrapper, and a run with a `File` when `/proc` is not a proc mount itself, a link to one included, as a file by that name there would run in its place (this last wrapping `errors.ErrUnsupported` too).
- `testenv`, wrapping the new `ErrRefused`: a `Rerun` or `RerunInterrupted` whose `ctx` has no deadline, or whose `outputCap` is below 1.
- `testenv`: a name given to `SkipOnWindows` that is not a top-level test's refuses the run.
- `service`, wrapping `ErrUsage`: on Windows a plan's `File` with a `Path`, and on every system a name that ends in `.` or is a Windows device name (above).
- `sandbox` on macOS: a profile or parameter the sandbox refuses is now an error that matches `ErrNoBlock`, with the sandbox's own first line, and the caller's program is not run. This one is made after a program starts: a dry run that starts only `/usr/bin/sandbox-exec` around `/usr/bin/true` (below).
- `load`: every system but Linux and macOS, and a source that cannot be read or parsed, return `ErrNoAverage`, which matches `errors.ErrUnsupported`.

### proc

- Added: `Cmd.Drain`, how long a run reads its output pipes after its tree is killed before it ends with `escaped`. It used to be a fixed 10 s.
  - A zero `Drain` is the default, 10 s, so a caller that sets nothing runs as before.
  - `Drain` bounds only the read of a pipe a process still holds, and is at least a quarter second there. A run whose tree left nothing holding its output pipes reads them to their end and ends without `WhyEscaped`, whatever `Drain` is, so a short `Drain` never cuts that output. A process started at the same moment for another run, which holds a copy of the pipe until its program begins, does not end the run as escaped.
  - A member the kill ended that still holds a pipe past the wait ends the run with `WhyEscaped` and `Left` true. With a `Drain` of 10 s or more, such a run no longer also ends with an `invalid argument` error, which came from asking again at the end of the wait about the pipe whose read the drain had already cut.
  - `Drain` never lengthens `Timeout`: `Run` returns at most `Timeout`, `Grace` and `Drain` after the program starts. On Unix a tree no signal reaches is waited for `Grace` and `Drain` past the kill, then left with `unkillable`.
- Added: `Limits.TreeMemory`, the memory the whole tree commits, held on Windows by the job, and `Limits.ProcessData`, each process's data segment (`RLIMIT_DATA`), held on Linux by the wrapper. The README has a table of what each limit holds on each system.
- Added: `Cmd.ExtraFiles`, open files the program inherits beyond its three streams.
  - On Unix entry i is its descriptor 3+i, as `exec.Cmd.ExtraFiles` gives it.
  - On Windows each handle goes to `AdditionalInheritedHandles` as it is. The caller marks it inheritable and tells the program its value.
- Added: `Cmd.File`, the program as an open file, so a file renamed over its name after it was opened is not the one that runs.
  - Linux alone runs one. The child execs `/proc/self/fd/<n>`, as glibc's `fexecve` does, with the file handed on after `ExtraFiles` and argv[0] its name.
- Added: `ErrBatch` and `ErrNotProgram` are exported. They are the refusals on Windows, by `Run` and `Start`, of a `Path` that names a batch file (`.bat` or `.cmd`) and of one that names no program file (`.exe` or `.com`), as given or as `PATHEXT` finds it.
  - Each wraps `ErrRefused` and neither matches the other, so a caller words each with `errors.Is` and no code of its own for Windows.
  - Both are declared on every system; off Windows no run returns either. What is refused does not change.
- Changed: a run's `Stdin` is told from a terminal by `golang.org/x/term`'s `IsTerminal`, in place of proc's own termios read and console-mode call. The MSYS and Cygwin pty pipe check is unchanged.
- Fixed: on Linux a program run with `Limits.ProcessData` or `Cmd.ReadPeak` starts with the signals its caller ignores ignored, as one run with neither does. Under v0.3.0's wrapper it started with `SIGTERM`, `SIGQUIT`, `SIGUSR1` and `SIGPIPE` at their defaults.
- Fixed, Windows: a run whose program starts nothing no longer reads `Left` true, at times on a loaded machine, when a process of its job ends between the job's listing of it and its opening.
  - Windows reads no image of a process that has ended while a handle to it is held (`ERROR_GEN_FAILURE`), nor, for some milliseconds, of one that has begun to exit (`ERROR_ACCESS_DENIED`).
  - The first is now taken for gone, as a pid no process has is, once its handle says it has ended. The second is waited for, as a console host is, once its exit code says it has begun to exit. In both, the job's count read again decides.
  - A process whose image cannot be read while its exit code says it is active is still left.
- Security: a run whose `Cmd.Stdin` is a nil `*os.File`, or a closed one, gives the program the null device, as a nil `Stdin` does. On Windows the program's stdin was a handle to the caller's own process, and on Unix it started with fd 0 closed, so the first file it opened was its stdin.
- Security: a `Detached` whose `Output` is a closed `*os.File` gives the program the null device for its stdout and stderr, as a nil `Output` does. On Windows they were a handle to the caller's own process, and on Unix the program started with fds 1 and 2 closed, so the first files it opened were its output.
- Security, Windows: the pipes a run makes for its program's stdin, stdout and stderr are no longer inheritable in the caller.
  - A process the caller starts another way during the run, handing on every inheritable handle, now holds none of them.
  - It used to hold the output pipes open, so the run ended with `WhyEscaped` and its output cut, and the stdin pipe, so the program did not see the end of its input.
- Security: a value stored in an exported error var, nil included, by a caller or a dependency, no longer changes what a gate refuses. Each gate returns, wraps and matches the value the var was built with.
  - `proc.ErrStale = nil` let `Stop` signal a process that took a reaped leader's pid.
  - The same holds for `proc.ErrRefused` and for the vars of `sandbox`, `service` and `load` (below).
  - No name or text changes. While no value is stored, `errors.Is` matches as before. After a store, a refusal matches the value the var was built with, not the one stored.
- Not held, Linux: a run through the wrapper, one with `Limits.ProcessData` or with `ReadPeak` armed, starts the wrapper from `/proc/self/exe` and, unlike a run with `Cmd.File`, does not check that `/proc` is a proc mount. In a root whose `/proc` is not the kernel's, whatever that path holds runs as the wrapper, so set neither there unless you would trust it as the wrapper.

### load (new)

- Added: `load.Read` reads the system load average: the one, five and fifteen minute averages, and `CPUs`, the CPU count.
  - Linux reads it through `github.com/shirou/gopsutil/v4/load`'s `Avg`, and falls back to `sysinfo(2)` when `/proc/loadavg` fails. It pins gopsutil's folder to `/proc` whatever `HOST_PROC` says.
  - macOS reads the `vm.loadavg` sysctl itself, since gopsutil's macOS build brings purego's `fakecgo` into every importer.
  - Windows, every other system, and a source that cannot be read or parsed return `load.ErrNoAverage`, which matches `errors.ErrUnsupported`.
  - It sets no threshold and starts no program.
- Security: a value stored in `load.ErrNoAverage` no longer changes what `Read` returns (as in `proc`).

### testenv

- Added: the package's test helpers.
  - `NoLeaks`, a run's leak check from the runtime's `goroutineleak` profile.
  - `Link`, `Links` and `NoLinks`: a link a test plants, or skips for by one message.
  - `Repo` and `GitPath`: a committed repository with links through git's index.
  - `Rerun`, `HelperTest`, `Helper`, `Signal` and `ErrEnded`: the helper-process practice. `Rerun(ctx, outputCap, args...)` takes both of its child's bounds from the caller, a deadline and a cap on each stream. A child that writes more than `outputCap` bytes to one stream is ended, with code -1, what it wrote up to the cap, and an error that is `ErrOutputCap`. `ErrRefused` and `ErrOutputCap` are new.
  - `TESTENV_HELPER` joins the names `Main` keeps.
- Added: `RerunInterrupted(ctx, outputCap, args...)` runs a helper as `Rerun` does, under the same bounds, and sends it the system's interrupt once it says it is ready with `Ready()`.
  - The interrupt is SIGINT on Unix, and CTRL_BREAK_EVENT to a process group of its own on Windows. Go hands it to the child as `os.Interrupt` on both, so a test of what a program does when interrupted needs no build tag.
  - A child that ends before it is ready, or that the interrupt cannot reach, gives the new `ErrNotInterrupted`.
- Added: `SkipOnWindows(names...)`, an option of `Main`, skips the named top-level tests on Windows from the caller's own code and runs them elsewhere. It replaces `windows-skips.txt` (above).
- Added: `Scale(t, base, limit)` stretches a test's wait by ten under `-race`, and by the one-minute load over the CPUs when that is above 1 (by race alone where `load` has no average). It is capped at `base * limit` and at `t.Deadline()`, and is never below `base`.
- Changed: `Git` takes its stripping from `gitenv.Env`, so a test's git child gets no `HOME`, `USERPROFILE`, `HOMEDRIVE`, `HOMEPATH` or `XDG_CONFIG_HOME`, beside no `GIT_` name but its own.
- `testenv` now imports `load` and `gitenv` of this module.

### service

- Changed: `Plan.Name` takes up to 230 bytes, where it took 128. 230 is the longest name Task Scheduler creates, as measured on Windows 10.0.26200, and every unit, plist and task file built from it fits. The characters it refuses are unchanged.
- Security: `Plan.Name` refuses a name that ends in `.` and a Windows device name, on every system (above).
  - Task Scheduler keeps a task as a file of its name. The package follows Win32's file naming rules, which drop a last `.` from a file name and read a device name, with or without an extension, as the device.
  - A native run on Windows 10.0.26200 found that schtasks keeps `app.` and `app` as two tasks. So this is the rule followed, not a collision seen.
- Security: a value stored in `service.ErrAbsent`, `service.ErrPercent` or `service.ErrUsage` no longer changes what is refused. `service.ErrAbsent = nil` gave a system with no tool an empty tool and no error.
- Not held, Windows: `Install` writes the task's XML to a new folder below the temp folder Go's `os.TempDir` gives (`TMP`, then `TEMP`, then `USERPROFILE`, and `C:\Windows\SystemTemp` for a process running as SYSTEM), and schtasks reads it there by path. The file is made new, so one already there fails the install, but the folder takes the temp folder's access: an account that may modify what is made below it can change the XML before the task is registered. Keep the temp folder private to the user.

### sandbox

- Fixed, macOS: `Run` and `RunHolding` set their profile in a dry run of `/usr/bin/sandbox-exec` around `/usr/bin/true`, through `proc.Run`, before the exec. A profile or parameter the sandbox refuses is now an error that matches `ErrNoBlock`, with the sandbox's own first line, and the program is not run. It used to be the sandbox's exit, 65, after the exec, which read as the program's own.
- Security: a value stored in `sandbox.ErrUsage` or `sandbox.ErrNoBlock` no longer changes what is refused. `sandbox.ErrUsage = nil` let `sandbox.Run` take a line it refuses.

### For programs that import go-proc

- The module requires two new modules: `golang.org/x/term` v0.47.0 (for `proc`) and `github.com/shirou/gopsutil/v4` v4.26.10 (for `load` on Linux). gopsutil brings in `github.com/ebitengine/purego`, `github.com/go-ole/go-ole`, `github.com/power-devops/perfstat` and `github.com/yusufpapurcu/wmi` as indirect requirements.
- The lint bans of `.golangci.yml` and of the library picks each state their security or correctness reason, and those whose reason was a preference are lifted.
  - These may now be imported: `howett.net/plist`, `github.com/rogpeppe/go-internal/testscript` and, in tests, `github.com/stretchr/testify` and `gotest.tools` (`testify/mock` stays denied).
  - `github.com/elastic/go-seccomp-bpf` stays denied, for two security reasons. Its arch guard falls through to the default ALLOW for i386 and AArch32, and it compares ioctl's request on 64 bits, which lets `TIOCSTI|1<<32` through. `golang.org/x/net/bpf` stays allowed.
  - `go-cmd/cmd`, `k8s.io/utils/exec`, `go-winjob`, `jobobject`, `kardianos/service`, `takama/daemon`, `libseccomp-golang`, `tailscale/wf`, `criyle/go-sandbox`, the clocks `benbjohnson/clock`, `clockwork` and `quartz`, `go-isatty` and gopsutil's `process` stay denied, each for its stated reason.

## v0.3.0 - 2026-11-17

Four names are added and none is removed or moved: `proc.Cmd.ReadPeak`, `proc.Result.Peak`, `proc.Result.PeakRead` and `proc.Result.Left`. Only `proc` changes. `proc.ErrRefused` is not new: each new refusal wraps it, and its message now names `ReadPeak` beside `Limits.Memory`.

### proc

- Added: `Cmd.ReadPeak` asks for the run's peak memory.
  - `Result.PeakRead` says whether a peak was read, so read it first. `Result.Peak` is the peak in bytes, or 0 when none was read.
  - Linux, macOS and the BSDs: the largest resident set of the program, or of a descendant it waited for.
  - Windows: the job's peak committed memory. That is not a resident set, so it is not comparable across systems.
  - No other system reads one. A run that is refused, ends `WhyUnkillable`, or whose program never ran reads none.
  - On Linux the program is started through a wrapper, this program started again, because a program Go starts carries its starter's peak into its own.
    - The run then needs `Cmd.Armed`, as `Limits.Memory` does: `main` and `TestMain` call `CappedExec(os.Args)` first and pass what it returns. Without it the run is refused.
    - It is also refused when the wrapper cannot open `/dev/null`.
    - The program still leads its own process group, which the run lists and kills whole. Under `NoTerminal` the wrapper leads the session.
    - The program starts with `SIGTERM`, `SIGQUIT`, `SIGUSR1` and `SIGPIPE` at their defaults, whatever the caller ignores.
    - With `Limits.Memory` too, the run still takes one wrapper.
    - The reading is never below the wrapper's own resident set once its package inits have run, a few MiB for most programs, since an exec carries that peak over.
- Added: `Result.Left` says whether the run's tree still held a process once the program had exited: one the program started and did not wait for.
  - The tree is still killed whole. `Code` and the error are the same either way.
  - On Linux and macOS the program's group is stopped with `SIGSTOP` before it is listed, so a chain of processes that fork and exit cannot slip past. A process that is exiting, or not yet reaped, counts.
  - On Windows it is the job's count of live processes after the program's wait. A console host Windows started for the tree is waited for, up to five seconds, when only such hosts are left.
  - A run ended by its `Timeout`, `MaxOutput`, its context or a limit reads `Left` as one whose program exited, once the kill has ended the program.
  - It reads true when the listing, the stop or the count fails. It also reads true on every BSD run, and for every run that ends `WhyUnkillable` or `WhyEscaped`.
  - Its limits: a process that left the tree, by `setsid` or `setpgid` on Unix or by breaking away from the job on Windows, is not seen unless it holds the run's output, which ends the run `WhyEscaped`. On Linux a process of another user that `/proc` hides (`hidepid`) is not seen either. So `Left` false does not prove that nothing was started.
- Fixed: a run whose `Stdin` is not a file now ends at its `Timeout` even if a Read of that `Stdin` never returns, as with an `io.Pipe` nobody writes to. It used to wait on that Read for ever.
  - `Run` copies the reader to the program through a pipe of its own, and stops waiting for the copy once the run ends. Ending a Read that never returns is up to the reader.
  - A reader that ends normally still reaches the program in full. An error the copy meets becomes the run's error when the program's exit gives none.
- Security, Windows: with `NoTerminal`, a `Stdin` that is the pipe of an MSYS or Cygwin pty is now refused. Git Bash's mintty gives a program such a pipe when its pseudo consoles are off.
  - Such a pipe is not a console, so it used to get through. A program that asks at its terminal, as an MSYS `ssh-keygen` asks for a passphrase, then asked the caller's user.
  - The pipe is recognised by its name: `\msys-<id>-pty<n>-from-master` or `-to-master`, or the same under `\cygwin-`.
  - Some cases are refused because the pipe cannot be told apart from a pty's:
    - a pipe whose name does not come within a second. Windows gives no name while a Read is pending on the pipe, as when the caller reads its own stdin in another goroutine. The name query then ends with that Read, so one thread stays held while the caller's Read is pending.
    - a `Stdin` whose type Windows does not give;
    - a pipe whose name Windows refuses to give, or gives with a length that does not fit.
  - The cost: a socket, or a pipe Windows gives no name, is refused under `NoTerminal`.
  - Still run:
    - a pipe with an empty name, as an `os.Pipe` end has;
    - a `Stdin` of handle 0, which is `os.Stdin` in a process with no stdin, such as a service or a detached program. The program gets no stdin.
  - A run without `NoTerminal` asks nothing of its `Stdin`.

## v0.2.0 - 2026-11-17

Three names are added and none is removed: `proc.Cmd.NoTerminal`, `testenv.Binary.Ldflags` and `testenv.Binary.Trimpath`. `testenv.Build` now refuses a package that `go build` would read as a flag.

### proc

- Added: `Cmd.NoTerminal` starts the program with no terminal of the caller's, in the run's tree as before. A program that asks at the terminal, as `ssh-keygen` asks for a passphrase, never asks the caller's user.
  - On Unix the program leads a session of its own with no controlling terminal, and opening `/dev/tty` fails at once.
  - On Windows it gets a console of its own that no window shows, and the console programs it starts share it.
  - A `Stdin` that is a terminal, or on Windows a console, is refused with it, by an error that wraps `ErrRefused`: a program that finds no terminal asks at its stdin instead.

### testenv

- Added: `(*Binary).Ldflags(flags)` and `(*Binary).Trimpath()` each return a new `*Binary` built with that flag. They are for a version golden (`-ldflags "-X main.version=..."`) and a reproducible-build check (`-trimpath`).
  - `Ldflags` takes one string, read the way `go build` reads it. It allows only the linker flags `-X`, `-s` and `-w` (bare, `=true` or `=false`) and `-buildid=<value>`.
  - It refuses, without running `go`, a bare `-buildid`, a value after a bare `-X` that starts with `@`, any other word, and any string that `go build` would split into other words than the check does. `Path` is then empty and `Run` gives code -1 with the reason.
  - A package is built once for each set of flags, and `-cover` under `GOCOVERDIR` still applies.
- Security: `Build` refuses a package that starts with `-`, which `go build` would read as a flag, such as `-toolexec=...` or an `-ldflags=...` that replaces the one `Ldflags` checked. No `go` runs, `Path` is empty and `Run` gives code -1 with the reason. This holds for every copy `Ldflags` and `Trimpath` make of it too.

### For programs that import go-proc

- Added: go-proc's lint names each package's job and the calls a program that imports it may no longer make by hand:
  - for `proc`: `os/exec`, `os.StartProcess` and the `syscall` start calls;
  - for `sandbox`: the other sandbox libraries;
  - for `service`: the other login-service libraries;
  - for `gitenv`: `os.Unsetenv` used to clear git's variables;
  - for `testenv`: `os.Setenv`, `os.Unsetenv` and `os.Clearenv`.
- go-proc's lint also records its own picks, and now refuses the libraries those picks replace, hand-made Landlock system calls, and raw `Syscall` calls outside a file built for one system.
- The README's systems table names Linux on arm64, tested as arm64 Linux in a container.

## v0.1.1 - 2026-11-15

A fix to `testenv`. A `go` that a test starts under `Isolate` now keeps the settings saved with `go env -w`, and on Windows the isolated folder is removed even after such a `go` has run. No name is added or removed.

### testenv

- Fixed: `Isolate` points `GOENV` at a copy of go's env file in its own folder, so a `go` a test starts reads the settings saved there with `go env -w`, such as `GOPRIVATE`, `GOPROXY` and `GOFLAGS`. A test's `go env -w` writes to the copy, never to the person's own file. Before this fix, `Isolate`'s configuration folder held no env file, so such a `go` ran without these settings and could not fetch a private module.
- The copy holds no credential. It leaves out:
  - the `GOAUTH` line;
  - every line with a URL that holds a user or a password;
  - a `GOPROXY` line that has such an entry anywhere in its list, with or without a scheme.
  A proxy that needs a password stays out of reach under `Isolate`, as before.
- A `GOENV` of `off` in the run's environment stays `off` (on Windows, however the name is cased). With no env file, `GOENV` is not set. A setting the run's shell sets over the file is not carried, just as no other variable of the shell is.
- `Clean` passes on a `GOENV` that is `off` or names a file in `Isolate`'s folder. It drops every other one, the person's own file among them.
- Fixed: `Isolate` turns go's telemetry off in its own configuration folder, so a `go` a test starts opens no counter file there and starts no upload process. Before this fix, `restore` on Windows could fail to remove the folder while such a file was still open.

## v0.1.0 - 2026-11-15

The first release of go-proc. It runs other programs and tests safely: a run with a deadline, an output cap and a whole-tree kill on every system, a detached tree that can be stopped later, a sandbox that holds a run to given folders and to Unix sockets where the system allows it, one login service through the system's own tool, and clean environments for tests and for git. It needs Go 1.27 and, beside the standard library, `golang.org/x/sys` and `github.com/landlock-lsm/go-landlock`.

### Moved here

Four packages were first written in an earlier module of the same authors and are here whole. A program that used them there changes the import path (and for `sandbox` the package name); the names below under "Removed" are the only ones that do not come with them.

- `gitenv`: moved unchanged.
- `testenv`: moved unchanged.
- `sandbox`: the package was named `netblock`, and is renamed; its names (`Run`, `RunHolding`, `Folders`, `ErrNoBlock`, `ErrUsage`) are the same.
- `proc`: from an earlier private module that was never published, so no public import path changes.

`service` is new.

### Removed

- `proc.Start(dir, env, cmd)`, the old form. Use `proc.Run` to run a program to its end; `proc.Start` now takes a `Detached` and starts a tree that outlives the caller.
- `gitenv.Names`. `gitenv.Env` drops every `GIT_` name, and `gitenv.Repo` only the names that point at a repository.
- `testenv.Leaks`. Use the options `testenv.Keep` and `testenv.Drop` of `Main` and `Isolate`.

### proc

- `Run(ctx, Cmd)` runs the program at `Path`, each of `Args` one argument, with a `Timeout`, a `MaxOutput` for each stream and, on Unix, a `Grace` between SIGTERM and SIGKILL. The program runs in a tree of its own, a process group on Unix and a Job Object on Windows, and the whole tree is killed when the run ends. A nil `Env` means `Bare()`. A run it ended returns an `Ended` that says why.
- A `Cmd` it cannot bound is refused with an error wrapping `ErrRefused`, and the caller's program is never started. On Windows that includes a file that is not an `.exe` or `.com`. Every refusal comes before anything starts but one: on Linux a run held to `Limits.Memory` first starts this program again as the wrapper that sets the cap, and when the wrapper cannot set it, the run is refused after the wrapper ran and before the program did.
- `Path` is the program itself, never a name looked up in PATH. A relative `Path` must hold a separator (`./tool`, `bin/tool`) and is resolved against `Dir`, or against this process's folder when `Dir` is empty. A bare name is refused, and so on Windows are `C:tool.exe` and `\tool.exe`, which Windows resolves against a current folder instead of `Dir`. The other refusals of `Path` are under Security.
- `Start(Detached)` starts a program out of the caller's session, terminal and console, in a tree that outlives the caller, and returns a `Tree`: its `ID` is the `TreeID` that `Stop` takes, and its `Leader` is the started process. `Leader.Wait` reaps the leader, and the id names nothing from then on; a caller that exits without that wait leaves the reap to the system. `Stop(id)` kills that whole tree. An id whose leader is gone or reaped is `ErrStale`, and nothing is signalled. On Linux the id also carries the boot, the pid namespace and the time namespace, so an id kept across a reboot or used in another namespace is `ErrStale`. On macOS `Stop` checks the leader again before each kill after the first; once the leader is no longer the process the id names, it stops killing the group and goes on process by process, each checked the same way, and says when a process may run on because the group outlived its last pass. On FreeBSD and the other Unix systems `Start` and `Stop` refuse.
- `Cmd.Limits` holds a run to `Memory` bytes and `Processes` processes where the system can; a limit it cannot hold is refused by name, never weakened. On Linux, `Memory` needs `main` and `TestMain` to call `CappedExec(os.Args)` first and pass the result as `Cmd.Armed`, and a `Memory` above the caller's hard data limit (`RLIMIT_DATA`), or with that limit unreadable, is refused before anything starts.
- On Windows, `Usage(id)` reads a tree's CPU time, counting its processes that have ended as well as those still running, and its count of live processes; `Pids(id)` lists its processes; and `JoinTree()` puts this process in a tree of its own and returns its id, which `Usage`, `Pids` and `Stop` take. A tree whose leader has exited is `ErrStale` to `Usage` and `Pids`. On every other system each returns an error wrapping `errors.ErrUnsupported`.
- Fixed: when a tree cannot be killed, `Run` returns `Code` -1 without reading process state a later reap may still be writing. On Windows a job's settings no longer live in memory a moved goroutine stack can leave behind; under load a test once read the job as having no flags.

### Security

What hardens a run, in one place:

- proc: `Run` and `Start` refuse an empty `Path`, which names no program; a `Path` holding `=`, which env-style launchers read as a setting and do not run; and a `Path` beginning with `-`, which they read as an option. Name a program whose name begins with `-` as `./-name`.
- proc: on Linux, `Start` and `Stop` refuse where `/proc` is not this pid namespace's own, or gives no boot id or namespaces, or its `NSpid` line does not name this process alone (a mount of an outer pid namespace, or a kernel before Linux 4.1), since the check of a tree's leader would then read a different process from the one the kill reaches. Nothing is started or signalled, and the error matches `errors.ErrUnsupported`.
- proc: on Linux a run held to `Limits.Memory` is refused with `ErrRefused` where the kernel would take the limit and not hold it: below Linux 4.7, where `ignore_rlimit_data` does not read `N`, and where the kernel's release cannot be read as a version or that setting cannot be read. The error also matches `errors.ErrUnsupported`.

- sandbox: on Linux the seccomp filter that holds sockets to `AF_UNIX` is set on every thread of the process, or the run is refused with an error matching `ErrNoBlock`; a filter the kernel did not attach is never taken as set. Each run proves its own block: an `AF_INET` socket is made before the block as a control and must meet the filter's refusal behind it.

### sandbox

- On Linux the folder rules are a Landlock ruleset built by go-landlock. It needs Linux 6.12 or later on amd64 or arm64, with Landlock ABI 6 and its erratum 2; anywhere else on Linux the run is refused.
- On Linux every run needs an `AF_INET` socket before the block, as its probe's control. Where the host already refuses one, such as a systemd unit with `RestrictAddressFamilies=AF_UNIX` or a container profile without inet, every sandbox run is refused.
- `Check(Folders)` says whether `Run` or `RunHolding` could set the block, and sets nothing and starts nothing.

### service (new)

- `Install`, `Remove` and `Query` have the system's own tool take, drop or report one login service or timer whose files the caller writes: `systemctl --user` on Linux, `launchctl` in the login session on macOS and `schtasks` on Windows, run through the caller's `Runner`. Only the tools' machine-readable answers decide the result.
- A name of anything but ASCII letters, digits, `.`, `-` and `_`, or a file outside `Folders()`, is refused with `ErrUsage` before anything is written or run. On Windows a task holding a `%` is refused with `ErrPercent`. On other systems every call is `ErrAbsent`.

### testenv

- `Main` and `Isolate` take options: `Keep(names...)` lets a variable through the allow list and `Drop(prefixes...)` removes a prefix. Calls with no options compile as before.
- `Build(pkg, opts...)` builds a program under test once and returns a `*Binary`, whose `Run` and `RunInput` methods run it. `Environ` and `Lookup` read the environment `Main` made, in place of `os.Environ` and `os.LookupEnv`.
- Fixed: on Windows, `Isolate` also points `USERPROFILE`, `LOCALAPPDATA` and `APPDATA` at its own folders, so a test cannot reach the Windows home and settings of the person running it.

### gitenv

- `Repo(environ, add...)` is the environment without the variables that name a repository, keeping the author and the rest, for a git child that writes. `Without(environ, prefixes...)` drops the names that start with a prefix. A test holds the list of repository names to what `git rev-parse --local-env-vars` prints.

### For people working on go-proc

Nothing here changes what a caller sees.

- `API.txt` lists every exported name, and the pre-push check fails when it and the source differ.
- go-proc has its own Taskfile, lint and release settings, with every tool pinned in `tools/`. The `pre-commit`, `pre-push` and `release` tiers run their checks side by side, each with a timeout, and fail past their budgets in `budgets.yaml` (2, 10 and 15 seconds). The `secrets` check fails where git reads no history of the tree's own.
- `sandbox` makes its openat2 call through `golang.org/x/sys/unix` instead of a raw system call.
- The GitHub release workflow runs only by hand, runs the release tier on Linux and Windows, and creates the release only when both pass.
- The tests of `gitenv`, `sandbox` and `proc` run under `testenv.Main`, and each package fails when its `TestMain` stops calling it. On Windows every process a test starts is in a job the test binary holds open, so none outlives a killed run.
